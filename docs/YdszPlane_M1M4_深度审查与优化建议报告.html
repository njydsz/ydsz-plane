核心发现

🎯 三大关键结论
  1. 后端引擎强劲，前端界面薄弱：Go 后端实现了 80% 的规划能力，代码质量高（Clean Architecture、统一错误处理、Outbox 事件机制），但前端大量视图停留在"骨架"级别（看板拖拽、WBS 树、富文本编辑等交互未真正打通），3 个后端已完成的模块（搜索、工作台、通知）前端完全未开发。
  2. Worker 是"纸老虎"：cmd/worker/main.go 中的 4 个 Task Handler（notifications.send / webhook.deliver / search.index / automation.evaluate）全部是空实现，仅打印日志。Outbox Relay 机制虽然就绪，但下游消费者为零，事件发布后无人消费。
  3. 测试负债严重：6 个测试文件、零 E2E、零集成测试、零前端测试，与架构文档规划的 "60% 单元 + 30% 集成 + 10% E2E" 金字塔差距巨大。

二、架构优化建议

P1 A1. 统一 Worker 消费端的"空壳"Handler

当前 worker/main.go 中注册的 4 个 Task Handler 全部是 log.Info + return nil 的空壳。这意味着 Outbox Relay 辛辛苦苦把事件投递到 RabbitMQ 后，没有任何实际业务被执行。建议立即补充：

  • notifications.send：接入邮件 SMTP 通道（邮件基础设施已就绪），实现基础站内通知写入 notifications 表
  • search.index：对接 PostgreSQL FTS 的 tsvector 生成（Issue 创建/更新时更新 GIN 索引）
  • webhook.deliver：虽然 Webhook 管理界面未做，但可以先搭建投递通道骨架
P1 A2. 引入 Repository 接口层，解耦 Application Service 与 pgx

当前所有 Service（issue/sprint/version/workspace）直接依赖 *pgxpool.Pool，SQL 散落在 Service 方法中。虽然没有立即拆微服务的需求，但从可测试性和长期维护角度建议：

  • 为每个聚合定义 Repository 接口（如 IssueRepository），将 SQL 查询封装在 internal/infrastructure/persistence/ 下
  • Service 依赖接口而非 pgxpool，便于单元测试时 mock
  • SQL 集中管理，便于后续做慢查询审计和索引优化
P2 A3. 建立统一的 API 响应 Envelope 中间件

架构文档要求 REST + 统一 envelope，但当前各 Handler 各自构造响应 JSON。建议实现一个 Gin 中间件或 helper，自动将返回值包装为 {"data": ..., "meta": {...}} 格式，统一分页、游标、错误格式。

P2 A4. 拆分 router.go，按域拆分路由注册

当前 internal/interfaces/http/router.go 混合了所有域的路由注册，可读性下降。建议按域拆分为 router_auth.go、router_issue.go、router_sprint.go 等，与前端 modules/ 目录对齐。

三、功能增强建议

3.1 M2 工作项核心 — 补齐交互深度

P0 F1. 集成 TipTap 富文本编辑器

架构文档明确选型 TipTap 3（ADR-8），当前工作项创建/详情表单中使用的是基础 <textarea>。对标 Jira/Linear/Plane，富文本编辑是工作项最基本的能力——支持 @提及、#引用工作项、代码块、图片粘贴。建议：

  • 在 packages/editor/ 封装 TipTap，产出 description_json
  • 同步实现 @提及解析器，为后续通知系统提供数据源
  • 先完成基础工具栏（粗体/斜体/列表/代码/链接），高级功能逐步迭代
P0 F2. 实现评论系统（issue_comments）

评论是协作的基本单元。S7 规划但当前毫无实现。建议：

  • DB 层 issue_comments 表已在架构设计中定义，需编写迁移脚本
  • 后端 CommentService（CRUD + 权限校验）
  • 前端工作项详情页底部评论列表 + 输入框
  • 与 TipTap 富文本复用同一编辑器组件
P0 F3. 实现附件上传（MinIO）

S7 规划。建议优先实现最小可用版本：

  • MinIO 客户端初始化（Docker Compose full profile 已支持）
  • 预签名上传 URL 生成端点
  • 前端图片粘贴上传 + 拖拽上传组件
  • 附件关联到工作项和评论
P1 F4. 完善看板视图的拖拽交互

当前 KanbanBoardView.vue 只有静态分列展示，拖拽流转未实现。建议使用 vuedraggable 或自研 DnD 实现：拖拽工作项卡片到目标状态列 → 调用 transition API → 乐观更新 UI。

P2 F5. 工作项批量操作

列表视图中缺少批量状态变更、批量分配、批量删除等操作，这对日常使用体验影响很大。

3.2 M3 迭代管理 — 补齐规划体验

P1 F6. Sprint Planning 拖拽实操化

SprintPlanningView.vue 框架就绪但拖拽交互未打通。Backlog ↔ Sprint 之间拖入/拖出是迭代规划的核心交互，建议优先实现。

P2 F7. 燃尽图接入 ECharts

当前 BurndownChart.vue 使用纯 SVG 实现，功能有限。建议切换到 ECharts，增加理想线、实际线对比、scope change 标注、趋势预测等标准燃尽图功能。

3.3 M4 版本日 — 补齐发布流程

P1 F8. 版本日发布向导走通端到端

VersionReleaseView.vue 三步向导（检查清单 → Release Notes → 确认发布）框架就绪，但需要打通真实数据流，包括清单项状态切换、Release Notes 模板渲染预览、准出校验结果展示。

3.4 M5 缺口 — 紧急补齐

P0 F9. 通知系统最小闭环

这是当前最大的体验缺口。建议分两阶段：

  • Phase A（2周）：站内通知 — notifications 表 + 后端 CRUD API + Worker 消费 Outbox 事件写入通知 + 前端铃铛组件（未读计数、列表、已读标记、点击跳转）
  • Phase B（后续）：邮件通知（复用 SMTP 基础设施）、通知偏好设置、digest 摘要
P1 F10. 前端搜索页面 + Ctrl+K 命令面板

后端搜索 API 已完整实现（search/service.go + 路由注册），但前端完全未开发。建议：

  • 顶栏搜索框 → 输入后调用搜索 API → 下拉结果分组（Issues / Sprints / Versions）
  • Ctrl+K 命令面板（参考 Plane/Liner/VSCode 交互模式）
  • 独立搜索结果页（/search?q=xxx）
P0 F11. 首页工作台实现

后端 Workbench API（workbench/service.go）已实现聚合查询（我的任务/迭代概览/最近访问/快捷操作），但前端 HomeView.vue 是空页面。建议立即对接，这是用户登录后的第一屏体验。

四、性能提升建议

P1 P1. 建立性能基线 — k6 压测

架构文档要求 "P95 API ≤200ms，100 万工作项"，但当前无任何性能测试。建议：

  • 编写 k6 压测脚本，覆盖核心接口：登录、Issue 列表/详情/创建、看板数据、Sprint 燃尽图
  • 编写 100 万工作项造数脚本（Go 并发 INSERT + COPY 协议）
  • 验证现有索引在百万级数据下的执行计划
P1 P2. Issue 详情缓存落地

架构设计定义了 issue:{id}:detail 10 分钟 Redis 缓存 + 事件失效，但代码中未见实现。建议在 IssueService.Get() 中落地缓存策略。

P1 P3. 看板查询优化

架构文档提到看板查询使用 (project_id, state_id, sort_order) 复合索引，需验证迁移脚本中是否已创建该索引。若缺失，百万级数据下看板查询将成为瓶颈。

P2 P4. 前端首屏加载优化
  • 路由懒加载（当前所有路由组件是同步 import）
  • Vite 代码分割（按域 chunk）
  • 首屏关键 CSS 内联
  • 接入 Lighthouse CI 建立性能预算
P2 P5. 数据库连接池与查询优化
  • pgxpool 配置化（当前硬编码 maxConns）
  • 对高频查询添加 prepared statement 缓存
  • 审计日志表按时间分区（避免单表膨胀）
  • issue_activities 表分区（架构文档已规划，未实施）

五、体验改善建议

P0 E1. 全页面空态/加载态/错误态走查

S7 MVP 加固计划之一，但当前并未系统性地在所有页面实现。建议以 checklist 方式过一遍全部 28 个页面：

  • 首次进入的空状态引导（如"还没有工作项，点击创建第一个"）
  • 数据加载中的骨架屏（当前部分页面无 loading 态）
  • 网络错误/权限拒绝的友好提示与重试按钮
P1 E2. 设计系统完善 — @ydsz/ui 组件库

当前 packages/ui/ 导出为空。10 个基础组件（AppButton/AppModal 等）虽然已实现，但分散在 src/components/ 下，未形成可复用的组件库。建议：

  • 将基础组件迁移到 packages/ui/src/，补充单元测试和 Storybook
  • 对 Element Plus 做正式的门面封装，页面层只依赖 @ydsz/ui
  • 完善设计令牌（与 Plane 设计语言对齐的颜色/间距/阴影/圆角体系）
P1 E3. 快捷键体系

对标 Linear/Plane，项目管理系统依赖高频快捷键提升效率：

  • Ctrl+K — 命令面板（跳转/创建/搜索）
  • C — 在当前视图中快速创建工作项
  • Esc — 关闭弹窗/侧面板
  • ↑↓ — 列表导航
  • 在 src/lib/shortcut.ts 中统一注册与管理
P2 E4. 视图偏好持久化

看板/列表的过滤器、排序列、分组方式应在用户刷新页面后保持。架构文档提到了"视图偏好随用户保存"，建议在后端 user_preferences 表或前端 localStorage 中实现。

P2 E5. 移动端响应式基线

移动端在 Phase 3 的 PWA 才规划，但基本的响应式适配（至少让页面在手机上可读）建议提前考虑，避免后期返工。

六、前后贯通建议

P1 I1. WebSocket 实时推送 — 打通前后端

这是"前后贯通"最大的缺失。架构设计完整定义了 WebSocket 方案（Redis Pub/Sub 扇出），但前后端均未实现。建议分步：

  • 后端：实现 WS Hub（Gin 集成 gorilla/websocket），订阅 Redis Pub/Sub 频道
  • 前端：实现 ws-client.ts（自动重连、心跳），在 WorkspaceLayout 挂载时建立连接
  • 初期事件：工作项状态变更、新评论、迭代进度更新
  • 前端联动：收到事件后精确失效 TanStack Query 缓存，看板无需整页刷新
P1 I2. 引入 TanStack Query (Vue Query) 管理服务端状态

架构文档明确规划使用 TanStack Query 管理缓存/失效/"避免手写 loading 态"。当前前端完全依赖 Pinia Store 手动管理加载态和缓存，代码冗余且易出错。建议：

  • 安装 @tanstack/vue-query
  • 为每个 API 调用封装 Query hooks（如 useIssues(), useSprint()）
  • 复用 WS 事件触发 queryClient.invalidateQueries()
P1 I3. 前端 API Service 与后端 Handler 对齐审计

整体对齐度较好，但以下端点前后端不一致：

  • 后端有 GET /search、GET /search/history、GET /search/bookmarks 等 10+ 端点 → 前端无对应 API Service
  • 后端有 GET /workbench 等端点 → 前端无对应 API Service
  • 后端 POST /api/v1/versions/:vid/release-notes/regenerate → 前端 version.ts 未对接
P2 I4. 生成 TypeScript 类型 — OpenAPI → TS

后端 Swagger 注解已覆盖全部端点，建议在 CI 中增加 openapi-typescript 自动生成前端类型定义，消除前后端类型不同步的风险。

七、过度设计分析与简化建议

⚠️ 以下是在当前阶段（M1-M4，未发布 MVP）存在过度设计倾向的领域

P1 O1. RabbitMQ 任务队列过早引入复杂重试机制

internal/infrastructure/mq/taskqueue.go 实现了封顶指数退避重试、死信队列路由、优先级调度等生产级特性，但当前 4 个 Task Handler 全是空壳。在 MVP 阶段，简单的轮询 + 线性重试已足够。建议：保持现有代码不动（后续有用），但不要在 MVP 前继续投入精力优化任务队列的高级特性。

P2 O2. 搜索方案过早规划 ES + IK 分词 + JQL 解析器

架构文档设计了完整的 ES 索引方案 + 类 JQL 语法解析器，但当前用 PG FTS 已经可以满足 MVP 阶段需求。建议：

  • MVP 阶段坚持 PG FTS（后端已实现），不要引入 ES
  • JQL 解析器延后到 Phase 2 用户反馈有强搜索需求时再做
  • 保留 search_documents 抽象层设计，为未来 ES 升级留接口
P2 O3. 信创方言层抽象过早

架构设计了 PostgreSQL / 达梦 / 人大金仓的方言抽象层（internal/infrastructure/persistence/dialect），但实际代码中未见方言抽象实现，仅文档层面规划。建议：

  • 在 MVP 阶段固定使用 PostgreSQL，方言接口仅定义但不实现
  • 等有实际信创部署需求时（Phase 3）再落地达梦/金仓适配
P1 O4. 架构文档与实现代码的"超前量"过大

14 份架构文档覆盖了从通知多管道到 DORA 效能度量的全部远景设计，但 M1-M4 实际只交付了核心域。大量文档描述的能力（仪表盘 10 种卡片、自动化 DSL、收件箱转正流程）在当前代码中无任何对应实现，可能给新加入的开发者造成"项目很完整"的错觉。建议：

  • 在每份架构文档开头明确标注"当前实现状态"（已在 02-架构开发详细计划中有标记，但其他文档缺失）
  • 考虑将远期设计移到单独的 docs/rfcs/ 目录，docs/architecture/ 只保留已实现或即将实现的设计
P2 O5. Docker Compose full profile（ES + MinIO）过早暴露

ES 和 MinIO 虽然标记为 optional profile，但在 README 快速开始中已经提到，用户可能期望这些功能可用。建议在 MVP 发布前将 full profile 相关文档暂时隐藏或明确标注"实验性/未实现"。
