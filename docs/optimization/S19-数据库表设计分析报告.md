## 1. 表结构一致性分析

### 1.1 发现的问题

#### 问题 C-01：user_roles.updated_at 注释错误（严重度：低）

**文件**：ydsz-plane-init.sql 第 2376 行

```sql
COMMENT ON COLUMN user_roles.updated_at IS '创建时间';  -- 错误，应为 '更新时间'
```

同一个 bug 在设计文档中也有（第 326 行文档写 `updated_at | TIMESTAMPTZ | DEFAULT now() | 创建时间`），说明是从模板复制时遗留的低级错误。不影响运行，但会导致开发者误解该字段语义。

设计文档将 intake_channels 标为 49、intake_issues 标为 50（1309-1355行）。SQL 中这两个表位于文件末尾补充区（5040 / 5060 行），与文档分类编排不一致。属于遗留编号问题不影响运行。

#### 问题 C-03：设计文档 users 表 updated_at 注释写为 "创建时间"（严重度：低）

设计文档第 269 行：`| updated_at | TIMESTAMPTZ | DEFAULT now() | 创建时间`

SQL 第 2334 行注释正确为 '更新时间'。设计文档与 SQL 实现不一致，需以 SQL 为准修正文档。

## 2. 索引设计审查

### 2.1 严重缺失索引（建议立即补充）

#### 问题 I-01：核心业务表缺少 tenant_id + created_at 排序索引（严重度：高）

**影响**：所有列表分页查询（"最新创建的任务/需求/缺陷"）需要该索引。无此 index 时 PostgreSQL 会对全表 filesort，数据量大时性能急剧下降。

```sql
-- 列表分页：按时间倒序
CREATE INDEX idx_task_tenant_created_at ON task (tenant_id, created_at DESC) WHERE NOT deleted;
CREATE INDEX idx_requirement_tenant_created_at ON requirement (tenant_id, created_at DESC) WHERE NOT deleted;
CREATE INDEX idx_defect_tenant_created_at ON defect (tenant_id, created_at DESC) WHERE NOT deleted;

-- 项目工作项维度 + 时间倒序
CREATE INDEX idx_task_project_created_at ON task (tenant_id, project_id, created_at DESC) WHERE NOT deleted;
CREATE INDEX idx_requirement_project_created_at ON requirement (tenant_id, project_id, created_at DESC) WHERE NOT deleted;
CREATE INDEX idx_defect_project_created_at ON defect (tenant_id, project_id, created_at DESC) WHERE NOT deleted;
```

#### 问题 I-02：notifications 收件箱查询索引 WHERE 条件与字段不匹配（严重度：高）

**文件**：ydsz-plane-init.sql 第 4840 行

```sql
-- 当前索引
CREATE INDEX idx_notifications_recipient ON notifications
    (tenant_id, recipient_id, is_read, created_at DESC)
    WHERE is_archived = false;  -- is_archived 未包含在索引键中
```

**问题**：部分索引的 WHERE 条件是 `is_archived = false`，但索引键列表包含 `is_read` 却不包含 `is_archived`。`is_read` 作为低基数布尔值放在索引第 3 列会降低索引效率。

```sql
-- 修正建议
CREATE INDEX idx_notifications_inbox ON notifications
    (tenant_id, recipient_id, created_at DESC)
    WHERE NOT deleted AND NOT is_archived;

CREATE INDEX idx_notifications_unread ON notifications
    (tenant_id, recipient_id)
    WHERE NOT deleted AND NOT is_archived AND NOT is_read;
```

#### 问题 I-03：看板查询缺少 tenant_id + project_id + state_id + sort_order 复合覆盖索引（严重度：高）

当前 4826 行已有：

```sql
CREATE INDEX idx_task_board ON task (project_id, state_id, sort_order) WHERE NOT deleted;
```

但看板高频查询包含 tenant_id 前缀隔离。现有索引缺少 tenant_id，导致回表过滤租户。

```sql
CREATE INDEX idx_task_board_tenant ON task (tenant_id, project_id, state_id, sort_order) WHERE NOT deleted;
CREATE INDEX idx_requirement_board_tenant ON requirement (tenant_id, project_id, state_id, sort_order) WHERE NOT deleted;
CREATE INDEX idx_defect_board_tenant ON defect (tenant_id, project_id, state_id, sort_order) WHERE NOT deleted;
```

#### 问题 I-04：sprints 缺少项目级时间范围查询索引（严重度：中）

```sql
CREATE INDEX idx_sprints_project_dates ON sprints
    (tenant_id, project_id, start_date, end_date) WHERE NOT deleted;
```

#### 问题 I-05：audit_logs 缺少按时间范围查询的索引（严重度：中）

```sql
CREATE INDEX idx_audit_logs_tenant_time ON audit_logs
    (tenant_id, created_at DESC) WHERE NOT deleted;

CREATE INDEX idx_audit_logs_action ON audit_logs
    (tenant_id, action, created_at DESC) WHERE NOT deleted;
```

#### 问题 I-06：三张 timelogs 表缺少按花费日期范围查询索引（严重度：中）

```sql
CREATE INDEX idx_task_timelogs_date ON task_timelogs
    (tenant_id, project_id, spent_date) WHERE NOT deleted;
CREATE INDEX idx_requirement_timelogs_date ON requirement_timelogs
    (tenant_id, project_id, spent_date) WHERE NOT deleted;
CREATE INDEX idx_defect_timelogs_date ON defect_timelogs
    (tenant_id, project_id, spent_date) WHERE NOT deleted;
```

### 2.2 冗余索引

#### 问题 I-07：idx_notif_subs_user 与 idx_notification_subscriptions_user_id 功能重叠

## 3. 字段可空性审查

### 3.1 严重问题

#### 问题 N-01：三张 comments 表的 updated_by 缺少 NOT NULL 约束（严重度：中）

```sql
-- 当前定义（第 515、1879、2065 行）
updated_by  BIGINT,  -- 可 NULL，但应为 NOT NULL DEFAULT 0
```

**业务影响**：评论编辑后 updated_by = NULL 会导致审计链断裂——无法追溯最后修改人。

```sql
ALTER TABLE task_comments ALTER COLUMN updated_by SET NOT NULL DEFAULT 0;
ALTER TABLE requirement_comments ALTER COLUMN updated_by SET NOT NULL DEFAULT 0;
ALTER TABLE defect_comments ALTER COLUMN updated_by SET NOT NULL DEFAULT 0;
```

#### 问题 N-02：audit_logs.actor_id 可 NULL —— 设计正确（严重度：无）

actor_id 允许 NULL（系统操作无 actor），workspace_id 也可 NULL（租户级操作），设计合理。

### 3.2 JSONB DEFAULT 建议

#### 问题 N-03：部分 JSONB 字段有 NOT NULL 但无 DEFAULT（严重度：低）

| 表 | 字段 | 当前 | 建议 |
|----|------|------|------|
| tenants | brand_config | JSONB (nullable) | 保持 |
| projects | modules | JSONB (nullable, no default) | 高频使用加 DEFAULT |
| task_comments | content_json | JSONB NOT NULL | **缺 DEFAULT** |

```sql
ALTER TABLE task_comments ALTER COLUMN content_json SET DEFAULT '{}';
ALTER TABLE requirement_comments ALTER COLUMN content_json SET DEFAULT '{}';
ALTER TABLE defect_comments ALTER COLUMN content_json SET DEFAULT '{}';
ALTER TABLE task_ext ALTER COLUMN field_value SET DEFAULT '{}';
ALTER TABLE requirement_ext ALTER COLUMN field_value SET DEFAULT '{}';
ALTER TABLE defect_ext ALTER COLUMN field_value SET DEFAULT '{}';
```

### 3.3 缺失字段

#### 问题 N-04：notifications 表缺少 workspace_id NOT NULL DEFAULT 0（严重度：高）

设计文档第 1073 行写明了 `workspace_id BIGINT NOT NULL`，但 SQL 实际创建的表缺少该字段。这意味着通知无法按工作空间隔离。

```sql
ALTER TABLE notifications ADD COLUMN workspace_id BIGINT NOT NULL DEFAULT 0;
```

## 6. RLS（行级安全）审查

### 6.1 现有覆盖范围

V26.09.26__rls_and_extensions.sql 声明 71 张表需要 RLS。对照 ydsz-plane-init.sql 中的 121 张表：

#### RLS 遗漏表

| 表 | 有 tenant_id | 建议 |
|----|-------------|------|
| intake_channels | 有 | 必须加入 |
| intake_issues | 有 | 必须加入 |
| sso_sessions | 有 | 建议加入 |
| role_permissions | 有 | 建议加入 |
| dlq_events | 有 (nullable) | 可选 |
| processed_events | 无 | 正确跳过 |
| schema_migrations | 无 | 正确跳过 |

#### 问题 R-01：intake_channels / intake_issues 未启用 RLS（严重度：高）

RLS 迁移文件 tables 数组缺少这两个表。含 tenant_id 且有业务数据（入口工单含 submitter_email），未启用 RLS 意味着应用层忘记 set_tenant() 时可跨租户读取其他租户工单。

```sql
-- 修复：在 RLS 迁移的 tables 数组中增加
'intake_channels', 'intake_issues',
```

### 6.2 策略完整性问题

#### 问题 R-02：RLS 策略只有 USING（读保护），无 WITH CHECK（写保护）（严重度：高）

当前策略（第 98-101 行）：

```sql
CREATE POLICY ... ON ... USING (tenant_id = get_tenant() OR tenant_id = 1)
```

**风险场景**：
```
SET app.current_tenant = '123';
INSERT INTO task (..., tenant_id) VALUES (..., 456);  -- 成功写入错误租户！
```

**修复**：

```sql
CREATE POLICY ...
    USING (tenant_id = get_tenant() OR tenant_id = 1)
    WITH CHECK (tenant_id = get_tenant() OR tenant_id = 1);
```

#### 问题 R-03：tenant_id = 1 的硬编码绕过（严重度：中）

tenant_id = 1 是默认共享租户，等于为所有系统默认数据开了一个 RLS 后门。

```sql
-- 方案 A：仅对超级管理员启用共享租户访问
USING (tenant_id = get_tenant() OR (tenant_id = 1 AND current_user = 'app_admin'))

-- 方案 B：移除 tenant_id = 1 条件，用单独策略替代
CREATE POLICY task_shared_read ON task FOR SELECT USING (tenant_id = 1);
```

#### 问题 R-04：sso_providers 列入 RLS 列表但实际无 tenant_id（严重度：低）

设计文档声明 "sso_providers 为系统级配置，不含 tenant_id"。SQL 实际创建的 sso_providers 表不含 tenant_id 列。RLS 迁移文件有 IF EXISTS (... column_name = 'tenant_id') 守卫不会启用 RLS。建议从 RLS tables 数组中移除 sso_providers 避免混淆。

-- 4. 迭代查询
CREATE INDEX idx_sprints_project_dates ON sprints (tenant_id, project_id, start_date, end_date) WHERE NOT deleted;

-- 5. 审计日志
CREATE INDEX idx_audit_logs_tenant_time ON audit_logs (tenant_id, created_at DESC) WHERE NOT deleted;
CREATE INDEX idx_audit_logs_action ON audit_logs (tenant_id, action, created_at DESC) WHERE NOT deleted;

-- 6. 工时报表
CREATE INDEX idx_task_timelogs_date ON task_timelogs (tenant_id, project_id, spent_date) WHERE NOT deleted;
CREATE INDEX idx_requirement_timelogs_date ON requirement_timelogs (tenant_id, project_id, spent_date) WHERE NOT deleted;
CREATE INDEX idx_defect_timelogs_date ON defect_timelogs (tenant_id, project_id, spent_date) WHERE NOT deleted;

-- 7. 通知收件箱
DROP INDEX IF EXISTS idx_notifications_recipient;
CREATE INDEX idx_notifications_inbox ON notifications (tenant_id, recipient_id, created_at DESC) WHERE NOT deleted AND NOT is_archived;
CREATE INDEX idx_notifications_unread ON notifications (tenant_id, recipient_id) WHERE NOT deleted AND NOT is_archived AND NOT is_read;

-- 8. JSONB GIN 索引
CREATE INDEX idx_projects_modules ON projects USING gin (modules jsonb_path_ops) WHERE modules IS NOT NULL AND NOT deleted;
CREATE INDEX idx_tenants_brand_config ON tenants USING gin (brand_config) WHERE brand_config IS NOT NULL;
CREATE INDEX idx_automation_rules_conditions ON automation_rules USING gin (conditions jsonb_path_ops);

-- 9. 清理冗余
DROP INDEX IF EXISTS idx_notif_subs_user;
