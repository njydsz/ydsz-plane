### 1.2 根本原因

swagger.yaml 由 `make swagger`（即 `swag init`）从 Go 源文件 `@Router` 注解生成。当前 `docs/swagger/swagger.yaml` 严重过期——包含大量**与当前 Go 源码不匹配的类型定义**：

- swagger.yaml 第 2–26 行把 `TokenPair.user.id` 标为 `integer`，**实际后端为 `string` UUID**
- swagger.yaml 第 16–26 行把 `UserBrief.id` 标为 `integer`，**实际后端为 `string` UUID**

最后一次 `make swagger` 似乎是在 `User` 与 `Auth` 模型改成 UUID 之前执行的，之后该步从未重跑。

## 4. 请求/响应不一致（核心接口抽样对比）

### P0-5：Auth 登录/注册响应 TokenPair 字段类型不一致严重度：P0

**后端**（`internal/interfaces/http/router.go:932` handler 返回 `*auth.TokenPair`；实际 TokenPair 定义见 `internal/application/auth/principal.go`）：

```go
type TokenPair struct {
    AccessToken  string    `json:"access_token"`
    RefreshToken string    `json:"refresh_token"`
    TokenType    string    `json:"token_type"`
    ExpiresAt    string    `json:"expires_at"`  // ISO8601 string
    User         UserBrief `json:"user"`
}
type UserBrief struct {
    ID          string    `json:"id"`           // ← UUID string
    Email       string    `json:"email"`
    DisplayName string    `json:"display_name"`
    AvatarURL   string    `json:"avatar_url"`
}
```

**前端**（`web/src/api/services/auth.ts:8-14`）：

```ts
export interface TokenPair {
  access_token: string;
  refresh_token: string;
  token_type: "Bearer";
  expires_at: string;
  user: UserBrief;
}
```

**问题**：
- `web/src/stores/auth.ts` 中的 `UserBrief` 接口若定义为 `id: number`，与后端真实运行时的 `id: string`（UUID）不一致。
- swagger.yaml（第 2–26 行）把标为 `integer`，进一步固化了错误认知。
- 运行时影响：若前端把 `id` 当 `number` 处理，UUID 格式会被 JS `Number()` 转换溢出成 `NaN` 或科学计数法，后续以 ID 为 key 的映射全部失效。

#### P0-6：Issue update reproduce_steps 双边数据类型不匹配严重度：P0

**后端 `updateIssueRequest`**（`internal/application/issue/handler.go:1777`）：
```go
ReproduceSteps json.RawMessage `json:"reproduce_steps,omitempty"`
```

**前端 `UpdateIssueInput`**（`web/src/api/services/issue.ts:207-211`）：
```ts
reproduce_steps?: {
    steps?: string;
    expected?: string;
    actual?: string;
};
```

**关键差异**：
- 前端发的是一个**结构化对象 `{steps, expected, actual}`**，JSON 序列化后变成 `{"steps":"...","expected":"...","actual":"..."}`
- 后端把这个值读入 `json.RawMessage` 后存入数据库/传给 service，但**handler 完全没有解析结构化字段**，只是把 RawMessage 原样传给 Service
- Service 层期望的 domain 类型与 RawMessage 之间的转换未在 handler 中完成，导致：
  - 写入数据库的值是不符合预期的 JSON 字符串
  - 读取时若强转为 struct 会 marshal 失败或字段丢失
  - 未来如果该字段参与业务逻辑（如缺陷阶段流转校验），会出现隐蔽的数据损坏

**修复建议**：
- 后端把 `updateIssueRequest.ReproduceSteps` 改为 `map[string]any` 或具名 struct `struct { Steps *string; Expected *string; Actual *string }` 以匹配前端
- 或前端把对象序列化成 string 再发

**根因**：codes.go 定义的常量是"前端 i18n key 映射"设计意图，但 service 层使用的是 errs 包中的哨兵变量，哨兵变量的 code**字符串格式**（如 `AUTH.TOKEN_EXPIRED`）与 codes.go 常量的 flat 格式（如 `AUTH_TOKEN_EXPIRED`）不一致。**codes.go 常量目前仅在少数 `WithCode()` 调用中被使用**，但由于命名不一致，很容易写出无效的 `WithCode(errs.CodeValidation)` 而实际运行时 code 与预期不同。

#### P1-7：Issue listIssues 响应 envelope 类型安全严重度：P1

**后端**（`internal/application/issue/handler.go:1121`）：
```go
c.JSON(http.StatusOK, gin.H{"results": results, "total": total, "limit": opts.Limit, "offset": opts.Offset})
```

**前端**（`web/src/api/services/issue.ts:305`）：
```ts
wrap<{ results: Issue[]; total: number; limit: number; offset: number }>(...)
```

**一致性**：当前 envelope 结构已对齐 ✅

**弱类型问题**：
- `total` 后端是 `int`，由 `int(total)` 转换，JS 中 `number` 类型超过 `Number.MAX_SAFE_INTEGER`（2^53-1）时可能精度丢失。实际使用中工作项总数很难超过此值，**风险较低**。
- `results` 裁剪时使用 `filterIssueFields` 做 `json.Marshal` → `map[string]any` → `json.Unmarshal` 双重转换（handler.go:1145-1174），带来不必要的性能开销且字段名依赖 Go struct tag；**一旦 Go 字段重命名，前端会静默地收到裁剪后的不同字段名**。

#### P1-8：Issue.parent_id TS 类型应为 number | null严重度：P1

- 前端 `Issue.parent_id` 声明为 `number`（issue.ts:39）
- 后端 `createIssueRequest.ParentID *int64`，当未传时 handler 第 573-574 行 `var parentIDPtr *int64; if req.ParentID != nil { parentIDPtr = req.ParentID }`，返回的 Issue 中 parent_id 在根工作项上为 `null`
- **建议**：`parent_id?: number | null`

#### P1-9：MemberResponse Swagger 类型与实际 DTO 不匹配严重度：P1

- swagger.yaml `workspaceMemberResponse`（第 90-102 行）包含 `display_name`, `email`, `id`, `joined_at`, `role`
- 但 `internal/interfaces/http/handlers.go:263` listMembers 的 Swagger 注解写的是 `@Success 200 {object} []interface{}`，过于宽松
- 运行时实际返回 Member 序列化后的 JSON，**与 swagger 中标注的 `workspaceMemberResponse` 假设一致**，但 handler 签名用了 `[]interface{}` 作为 result 静态类型，Swagger 文档丢失了字段级约束

### 5.2 前端 api/errors.ts 处理逻辑

文件：`web/src/api/errors.ts`（共 105 行）

```ts
export class ApiError extends Error {
  code: string;
  fields: Record<string, string>;
  statusCode: number;

  get isValidation() { return this.statusCode === 422; }
  get isAuth() { return this.statusCode === 401; }
  get isForbidden() { return this.statusCode === 403; }
  get isNotFound() { return this.statusCode === 404; }
  get isRateLimited() { return this.statusCode === 429; }
  get isNetwork() { return this.statusCode === 0; }
}
```

**特性**：
- 前端**仅按 HTTP status code 粗分类**，没有对后端 27 个错误码做 switch/case 匹配
- 后端 27 个 Code 常量在 TS 端**完全未被 import 或引用**——属"已注册未消费"状态
- error.code 被透传到 UI，但 UI 层无对应的 i18n key 映射

#### P1-10：codes.go 27 个常量在前端 errors.ts 零消费严重度：P1

**设计意图**（`pkg/errs/codes.go:1-18`注释）：前端 i18n key 与后端 code 一一对应，实现"例如 `AUTH.TOKEN_EXPIRED` → 自动匹配 `error.auth.tokenExpired` 中文翻译"。

**实际状态**：errors.ts 只按 `statusCode` 粗分类，完全不做 code 匹配；前端 i18n `web/src/locales/zh-CN.ts` 中未找到针对任何 27 个中错误码的映射。

**迁移状态**：卡在设计意图 → 落地之间；codes.go 成为死代码常量。

#### P1-11：前端 401 刷新令牌失败的错误码路径未对齐严重度：P1

`web/src/api/client.ts:186`：刷新失败时构造：
```ts
return Promise.reject(new ApiError({ code: "AUTH.EXPIRED", message: "登录已过期，请重新登录" }, 401));
```

但后端刷新失败实际返回 `AUTH.TOKEN_EXPIRED`（errs.go:285）或 `AUTH.UNAUTHORIZED`（errs.go:240）。  
前端自己构造了一个**不存在于后端的错误码** `AUTH.EXPIRED`，与 codes.go `CodeAuthTokenExpired = "AUTH_TOKEN_EXPIRED"` 也不能直接匹配。

#### P1-12：错误详情在 envelope 结构中的位置不一致严重度：P1

- 前端 `ApiEnvelope`（errors.ts:18-25）在 `request_id` 位于 **error 对象体内**：`{ error: { code, message, details?, request_id? } }`
- 后端实际由 middleware（router.go:606）注入到 **HTTP Header `X-Request-ID`** 而非 envelope 体内
- 前端 auth.ts:35 从 `r.headers["x-request-id"]` 读取 requestId（正确），但 errors.ts 的 ApiEnvelope 接口把 request_id 放在体内（无形中暗示两种位置都可能），若未来有工程把 requestId 改回 body，会破坏前端解析

#### P2-1：details 字段名一致严重度：P2

- 前端 `ApiErrorDetailItem`（errors.ts:12-15）：`{ field: string; reason: string }`
- 后端 `FieldDetail`（errs.go:75-83）：`{ Field string; Reason string }`
- JSON 序列化后一致 ✅ 无问题

## 6. 其他贯通问题

### P1-13：CSRF 双提交 Cookie 机制 - 前后端字段名对齐

- 前端 `client.ts:114-117` 从 Cookie `X-CSRF-TOKEN` 写入 Header `X-CSRF-Token`

- 后端持久化 Cookie 名 `X-CSRF-TOKEN`（routing.go:613）
- **大小写差异**：HTTP Header 大小写不敏感，运行正常。✅ 一致。

### P2-2：contentTemplate.ts URL 硬编码 /api/v1 前缀

- 前端所有 URL 都以 `/api/v1/...` 开头，但 axios baseURL 也是 `/api/v1`
- axios 在发现传入 URL 以 `/` 开头时视为绝对路径，不补 baseURL——所以不会重复
- 但仍属不规范写法，建议移除硬编码前缀以复用 baseURL

### P2-3：workspaceApi 部分 method 返回类型过于宽泛

`project.ts:85` 的 `listProjectMembers` 返回类型标注为 `Project[]`：
```ts
listProjectMembers: (wsId: number, projectId: number) =>
    wrap<Project[]>(http.get(`/workspaces/${wsId}/projects/${projectId}/members`))
```
但**实际上后端返回的是 member 数组**（含 id/email/display_name/role/joined_at 字段），不是 Project 数组。类型与 `workspace.ts:168` 中使用的 `Member[]` 不一致，应修正为 `Member[]`。

### P2-4：Issue.parent_id TS 类型严重度升级

见 P1-8，前端 interface 应修正为 `parent_id?: number | null` 以匹配后端 `*int64` 语义。
