## 二、七大维度可落地优化建议

### 维度一：数据库表设计优化

#### 2.1.1 多态残留治理与表结构归一化 【P1】

**现状**：S17 指出 database 已做去多态改造，但仍有部分冗余列/表需要治理。当前 121 张表数量较多，部分 xxx_requirements / xxx_tasks / xxx_defects 关联表可归一化。

**对标**：Jira 的 Issue 单表 + 类型字段模式（avltree 索引）、阿里的《阿里巴巴 Java 开发手册》单表字段上限建议。

**建议**：

```
1. sprint_requirements / sprint_tasks / sprint_defects 三张关联表
   → 统一为 sprint_issues（带 type 字段区分，对齐 issues 主表设计）

2. issue_assignees / requirement_assignees / task_assignees / defect_assignees
   → 确认是否已合并为 issue_assignees（S16 推进的去多态工作）

3. 表数量控制：目标 ≤80 张核心业务表（精简关联表）

4. JSONB 字段索引审计：
   - description_json 已使用 GIN 索引
   - 其余 JSONB 字段按需添加表达式索引
```

**预估工期**：2-3 天（含迁移脚本 + 测试验证）

---

#### 2.1.2 索引健康度审计与慢查询防护 【P1】

**现状**：当前有 121 张表，但索引设计主要基于文档预定义，缺少运行时统计反馈。

**对标**：美团 DBA 规范（表必须有主键、索引必须有针对性、慢查询周巡检）、阿里云 RDS 最佳实践。

**建议**：

```
1. 启用 pg_stat_statements 扩展，采集慢查询 Top 20
2. 创建索引使用监控系统（pg_stat_user_idx 视图）
3. 自动化脚本：每周输出新增慢查询、索引命中率变化
4. 大表（issues/activities/comments）定期 VACUUM ANALYZE
5. 复合索引前缀对齐高频查询模式（project_id + deleted + state_id）
```

**预估工期**：1-2 天（脚本+监控配置）

---

#### 2.1.3 数据生命周期管理 【P2】

**现状**：所有数据无保留期限，webhook_logs 虽有 30 天计划但未见实现。

**对标**：Jira 的 "Audit log" 归档策略、PostgreSQL 原生分区表（ declarative partitioning ）。

**建议**：

```
1. webhook_logs / audit_logs 按月份声明式分区（原生 PG 分区）
2. domain_events 已发布事件归档至历史表（30 天后归档）
3. 软删除数据自动清理：deleted_at < now() - interval '1 year' 物理删除
4. Outbox 发布后自动清理（published_at 非空超过 24h 归档）
5. 前端"回收站"功能：工作空间级删除恢复（30 天窗口期）
```

**预估工期**：3-4 天（分区表 + 清理策略 + 回收站 UI）

### 维度二：接口测试与质量保障

#### 2.2.1 补全 swaggo 注解覆盖率 【P0】

**现状**：`docs/swagger/swagger.yaml` 仅覆盖认证/工作空间等基础端点；issue/sprint/version/automation 等核心域缺失。

**对标**：Stripe API 文档标准、GitHub API OpenAPI 规范、美团接口文档完备率要求。

**建议**：

```
1. 按域分批补全 @Summary @Description @Param @Success @Failure @Router 注解
2. 引入 swaggo 覆盖率门禁：`make swagger-coverage` 计算注解覆盖率，目标 ≥90%
3. 每个新 Controller 上线前必须带 swagger 注解（CI 强制检查）
4. 每个端点必填 x-permission（所需权限点）、错误码示例
5. API 错误码文档自动生成（codedoc 工具）
```

**预估工期**：2-3 天

---

#### 2.2.2 Playwright E2E CI 真实运行 【P0】

**现状**：`web/e2e/` 已有 13 个 spec 覆盖 state-machine/webhook/安全/搜索/通知等核心路径，但 CI 中未真实运行。

**对标**：项目 DoD 声称 "E2E 覆盖核心路径"、美团前端 E2E 覆盖率要求。

**建议**：

```
1. 新增 Playwright CI job（复用 Go 测试的 postgres+redis 服务矩阵）

3. 视觉回归：关键页面截图对比（storybook + playwright）
4. E2E 失败自动上传 trace（`npx playwright show-trable` 离线下载查看）
5. 覆盖率合并：unit + integration + e2e 三档覆盖率综合评分
```

**预估工期**：1-2 天

#### 2.2.3 领域层 Mock 化集成测试 【P1】

**现状**：已有 30+ Go 测试文件，但集成测试依赖真实 PG/Redis。S16 P0-2 Repository 接口已抽象，但 Mock 化测试未铺开。

**对标**：Uber Go Style Guide "Test Doubles"、Google SWE 测试金字塔、阿里单元测试规范。

#### 2.3.2 any 类型治理 【P1】

**现状**：非测试文件 98 处 `any`，集中在 CommandPalette.vue、GlobalSearch.vue、FocusModeView.vue；domain service 中 `Record<string, any>` 占主体。

**对标**：美团前端 TS 规范（`@typescript-eslint/no-explicit-any: error`）、Total TypeScript 倡导的严格类型。

**建议**：

```
1. ESLint 叠加 @typescript-eslint/recommended-type-checked 严格规则
2. any → unknown + 类型守卫迁移（分批进行，ratchet 只降不升）
3. 高频场景定义共享类型：FilterParams、SortConfig、PaginationCursor
4. CI 添加 any 计数 ratchet：max_any_count: 50（逐步收紧到 0）
5. 优先治理：api/services/（类型生成）、stores/（状态类型）、composables/（逻辑复用层）
```

**预估工期**：2-3 天

#### 2.3.3 API 客户端拦截器增强 【P1】

**现状**：`web/src/api/client.ts` 已实现基础拦截（X-Request-ID、401 刷新、429 限流），但缺少 TanStack Query 集成、乐观更新、离线队列。


**预估工期**：2-3 天

### 维度四：架构优化

#### 2.4.1 issue 模块拆分（按子域）【P0】

**现状**：`internal/application/issue/` 膨胀至 40+ 文件，handler.go 65.7KB。需求/任务/缺陷混在同一目录，职责边界模糊。

**对标**：Uber Go Style Guide "Single Responsibility"、阿里模块拆分规范、DDD 限界上下文。

**建议**：

```
internal/application/issue/
  ├── shared/              # 通用：models.go、cross_type_union.go、metrics.go、workitem_cache_service.go
  ├── requirement/         # 需求子域：requirement_service.go + requirement_handler.go
  ├── task/                # 任务子域：task_service.go + timelog_service.go + task_handler.go
  ├── defect/              # 缺陷子域：defect_service.go + defect_analytics.go + defect_handler.go
  ├── interfaces.go        # IssueModule 组合接口（不变量约束）
  ├── relation/            # 工作项关联：relation_service.go、activity_service.go
  ├── import/              # 导入导出：import_service.go、export_service.go
  └── comment/             # 评论：comment_service.go、comment_sanitize.go
```

**预估工期**：2-3 天（文件拆分 + 接口抽取 + 测试验证）

### 维度五：性能提升

#### 2.5.1 BatchUpdate 事务包裹与 Saga 补偿 【P0】

**现状**：S16 BatchUpdateV2 优化 DB 往返，但每个 ID 单独事务，部分失败时态不一致。

**对标**：阿里《Java/Go 规范》事务边界最小化但保证一致。

**建议**：

```
1. 批量操作加整体事务包裹（单事务 ≤100 条 SQL，避免长事务）
2. 失败详细日志：逐条记录失败原因，返回 200 + results[].status 明细
3. 大批量（>500 条）拆分为多个子事务，失败部分回滚
4. 引入 Saga 补偿模式（独立回滚记录表）处理跨聚合操作
5. 批量操作超时控制：默认 30s，超时自动转为异步任务
```

```

3. 错误自动上报：500 错误触发 Sentry（已有 sentry 模块）
4. 访问日志：userId、workspaceId、method、path、status、latency 结构化输出

```

**预估工期**：1 天

### 4.4 数据库迁移回滚验证 【P1】

### 4.5 健康检查三级体系 【P2】

## 七、总结

### 7.1 Ydsz Plane 核心优势

1. **信创合规独家**：国密 SM2/SM3/SM4 + 达梦/人大金仓适配，这是 Jira/Linear/云效 不具备的能力
2. **架构成熟度高**：Outbox 事件驱动 + RLS 行级安全 + 蓝绿 Reindex，对齐 Google SRE 最佳实践
3. **工程规范完善**：96 条 AI 编码规范 + 完善架构文档（18 篇设计文档）+ 测试金字塔策略
4. **功能覆盖全面**：需求/任务/缺陷/迭代/版本/看板/甘特/日历/仪表盘/自动化/搜索

### 7.2 主要差距（对标 Jira Cloud / Linear）

1. **搜索深度**：缺 AI 语义搜索和 Completion Suggester（可通过 pgvector + ES kNN 补齐）
2. **自动化可视化**：缺拖拽规则构建器和 Marketplace（MVP 可 5-7 天交付）
3. **集成生态**：缺入站集成市场（Phase 3）
4. **移动端体验**：缺原生 App/PWA（3-5 天可 PWA MVP）

### 7.3 升级路径

当前成熟度：**Jira Cloud 75% + Linear 70%**

经过 S18 四个阶段落地后目标：**Jira Cloud 85% + Linear 85%**

核心提升维度：
- 安全：从"基础合规"到"零遗留"
- 性能：从"P95 200ms"到"P95 150ms"
- 体验：从"功能齐全"到"使用愉悦（对齐 Linear 90%）"
- 智能化：从"规则引擎"到"AI 辅助决策"
