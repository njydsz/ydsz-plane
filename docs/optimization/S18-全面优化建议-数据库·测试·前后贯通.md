## 一、数据库表能力设计分析

### 1.1 现状概览

| 维度 | 数值 | 评价 |
|------|------|------|
| 总表数 | 121（含 13 个 ENUM 类型） | 覆盖完整，对标 Jira 约 75% |
| 索引总数 | 231 | 密度适中（~1.9 索引/表） |
| 触发器 | 2（set_updated_at / bump_version） | 基础必备已到位 |
| 部分索引（partial index，WHERE NOT deleted） | ~58 个 | 软删除查询优化良好 |
| JSONB 列 | 75 处 | 灵活但需警惕过度使用 |
| UUID public_id 列 | 42 处 | 分布不均，核心表覆盖不足 |

### 1.2 架构设计优点

- **三层次隔离（tenant_id → workspace_id → project_id）**统一且一致，所有业务表均具备，为 RLS 打下基础。
- **应用层雪花 ID 生成 + 无物理外键**：符合互联网高并发设计惯例，避免外键锁争用。
- **软删除 + 部分索引（WHERE NOT deleted）**：查询性能有保障。
- **乐观锁（version 字段）**在 issues / sprints / versions 等高并发表上已部署。
- **领域事件表 domain_events + Outbox 模式**：已就绪，异步事件链路有基础。
- **search_documents.tsv 全文检索 tsvector**：原生 PG 全文搜索已集成。

### 1.3 关键问题与改进建议

#### 1.3.1 表型工作项设计（Task/Requirement/Defect 三表分立）—— 架构级优化

**现状**：`task`、`requirement`、`defect` 三张独立表存储 90% 相同字段（约 30 列重复）。每张表各自的 comments / labels / modules / watchers / relations / ext 子表也因此三份镜像（共 18 张子表）。设计与 `docs/architecture/04-数据模型设计.md §3.1 issues（系统最核心的表）` 描述的「单 issues 表 + type_code 区分」严重背离。

**问题**：
- 新增通用字段（如 `custom_field_1`）需改 3 张主表 + 修改 API / Handler 层若干分支逻辑；
- 跨类型联合查询（如工作台「我的待办」跨 requirement+task+defect）需要 UNION ALL；
- 全文检索 search_documents 索引需三路分别 upsert。

**建议（P0 高价值 / 工期 2-3 周）**：

按架构文档 §3.1 收敛为单 `issues` 表：

```sql
CREATE TABLE issues (
  id            BIGINT PRIMARY KEY,
  type_code     VARCHAR(20) NOT NULL CHECK (type_code IN ('requirement','task','defect', 'epic')),
  -- 公共字段（约 30 列）
  -- defect 专有（severity, found_phase, ...）NULLABLE
  -- task 专有（category, delay_reason）NULLABLE
  -- requirement 专有（source, acceptance_criteria）NULLABLE
  CONSTRAINT defect_required CHECK (
    type_code <> 'defect' OR (severity IS NOT NULL AND found_phase IS NOT NULL)
  )
);
```

子表合并为 `issue_comments / issue_labels / issue_modules / issue_watchers / issue_relations / issue_ext`。

**迁移路径**：新建 issues 表 → DB 层 VIEW 兼容旧接口 → API 层双读双写 → 后台迁移任务 → 切读 → 停写旧表 → 删旧表。无需停机。

---

#### 1.3.2 RLS（行级安全策略）缺失 —— P0 安全合规

**现状**：架构文档 §13 明确 RLS 是核心安全机制，所有表也都有 `tenant_id` / `workspace_id`，但 `sql/ydsz-plane-init.sql` 中**零 RLS POLICY、零 ENABLE ROW LEVEL SECURITY**。依赖应用层 middleware 校验租户归属，存在遗漏风险。

**对标**：架构设计 §13、等保三级、Postgres Official RLS Best Practice。

**建议**：

```sql
-- 以 issues 表为例（假设已合并为单表）
ALTER TABLE issues ENABLE ROW LEVEL SECURITY;
CREATE POLICY issues_tenant_isolation ON issues
  USING (tenant_id = current_setting('app.current_tenant')::BIGINT);

-- 设置租户的 PostgreSQL 函数（非-superuser 安全）
CREATE OR REPLACE FUNCTION set_tenant(p_tenant BIGINT) RETURNS VOID AS $$
BEGIN
  PERFORM set_config('app.current_tenant', p_tenant::TEXT, false);
END;$$ LANGUAGE plpgsql SECURITY DEFINER;
```

每次请求从 middleware 调用 `SELECT set_tenant(?)`。对 121 张表批量生成可用脚本化。**预估工期 2-3 天（含回归测试）**。

#### 1.3.3 ID 体系不一致 —— P1

**现状**：

- 121 表中仅 ~42 处有 UUID `public_id`，其余表缺少外部引用安全 ID；
- `architecture/04-数据模型设计.md` §1 规定 `BIGINT GENERATED ALWAYS AS IDENTITY` 但 SQL 实际使用 `BIGINT PRIMARY KEY` 应用层雪花。

**建议**：

- 统一策略：所有对外暴露的 API 资源使用 `public_id UUID`，内部主键用 BIGINT 雪花（与现有雪花 ID 不冲突）；
- `users`、`workspaces`、`projects` 等核心表缺少 `public_id`，需按域分批补齐；
- 迁移脚本：`ALTER TABLE xxx ADD COLUMN public_id UUID DEFAULT gen_random_uuid() UNIQUE NOT NULL;`

**预估工期**：1-2 天（分域推进）。

---

#### 1.3.4 JSONB 字段缺乏约束治理 —— P1

75 个 JSONB 列是真·动态结构，但以下字段实质上是半结构化且高频过滤，会影响查询性能且无法建索引：

| 字段 | 所在表 | 建议 |
|------|--------|------|
| `brand_config` | tenants | 提取 `primary_color` / `favicon_url` 为独立列 |
| `config` | workspaces / projects | 提取 `default_view` / `feature_flags` 为独立列 |
| `description_json` | issues / task / requirement / defect | 全文检索走 `description_stripped`，不依赖 JSONB |
| `reproduce_steps` | defect | 若 `{steps, expected, actual}` 结构稳定，提取 `steps_md` 为 TEXT 列 |

通用建议：**Postgres CHECK 约束 + jsonschema 校验**（应用层落地，禁止 malformed JSONB 入库）。

---

#### 1.3.5 Search Indexer 与主数据一致性 —— P1

`search_documents` 表是 ES Fallback 或搜索加速，但：

- 没有与主表的 **CDC（Change Data Capture）** 自动同步机制；
- 依赖 Outbox 表格手动消费，故障窗口内搜索数据滞后。

**建议**：引入 Debezium / pg_logical → Kafka → search-indexer，或至少 Outbox Worker 断点续传告警（Lag > 5min 触发告警）。

---

#### 1.3.6 数据库扩展（Extensions）引用为 0 —— P2

没有启用任何 PG 扩展。建议按需启用：

```sql
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";       -- UUID 生成（已有 pgcrypto 替代可跳过）
CREATE EXTENSION IF NOT EXISTS "pg_trgm";         -- 模糊搜索 / 相似度
CREATE EXTENSION IF NOT EXISTS "btree_gin";       -- GIN 复合索引
CREATE EXTENSION IF NOT EXISTS "pg_stat_statements"; -- 慢查询统计
```

#### 2.3.4 集成测试架构不够健壮

现有集成测试使用 `YDSZ_TEST_DATABASE_URL` 环境变量门控，正确但仍有问题：

- **数据清理依赖 t.Cleanup**：如果测试崩溃（panic），清理代码不执行，数据库残留脏数据；
- **无并行执行**：所有集成测试串行，CI 时间随用例增长线性增加；
- **没有事务回滚方案**：大量造数 + 清理周期长。

**建议**：

1. 引入 `testify/suite` + 事务型测试夹具（每个测试 begin tx → 测试 → rollback）；
2. 使用 `dockertest` 在 CI 中按需启动 PG/Redis 容器，避免手工准备；
3. 集成测试与单元测试分层：`go test -short` 跑纯单元，CI pipeline 单独跑集成。

### 3.1 现状概览

| 维度 | 数值 | 评价 |
|------|------|------|
| 前端视图 | 82 个 Vue 文件 | 覆盖全部核心视图 |

| E2E 测试 | 12 个 Playwright Spec | 核心路径已覆盖 |
| Swagger 路径覆盖 | **约 7 个 API path** orval 全量生成不可用 | 🔴 严重不足 |

### 3.2 核心问题

#### 3.2.1 OpenAPI 标注率 <10%，orval 无法生成 🔴

`orval.config.ts` 注释明确指出「swagger 注解覆盖率 <10%，仅 7 个 path」。实际上 `docs/swagger/swagger.yaml` 只有 290 行，而 gin router 注册了 30+ 个 Register 函数、覆盖 100+ 个 API endpoint。

**后果**：

- 前端 33 个 service 文件全部**手写的 TS interface**（如 `Issue`、`Sprint`、`State`），可能与后端 DTO 漂移；
- 字段增删没有编译期保障，只能靠 E2E 冒烟发现；
- API 版本演化时 breaking change 无法自动发现。

**建议**（按美团/字节 API 治理惯例）：

| 步骤 | 说明 | 工期 |
|------|------|------|
| 1. 补齐 swaggo 注解 | `@Summary @Description @Accept json @Produce json @Param @Success @Failure @Router` | 3-4 天 |
| 2. CI 门禁 | `swag init` 后 diff 检查；覆盖率从 10% 逐域推进到 80%+ | 0.5 天 |
| 3. orval 全量生成 | 取消 `orval.config.ts` 注释屏蔽，目标 `src/api/generated/*` | 0.5 天 |
| 4. service 渐进式迁移 | 手工 interface → 生成的 `ApiResponse<T>`，按域分批 PR | 1-2 周 |

**注意**：注解补齐是「一次投入、长期受益」——后续新 Controller 上线时必须带 swagger 注解作为 DoD 卡点。

---

#### 3.2.2 Backend DTO / Frontend Interface 对齐漂移 🔴

抽样对比发现多处潜在漂移：

| 字段 | 后端 Issue 结构 | 前端 Issue Interface | 差异 |
|------|----------------|---------------------|------|
| `public_id` | `string (UUID)` | `string` | ✅ 一致 |
| `description_stripped` | 后端 select 使用 | 前端 **缺失** | 🔴 前端用 description_html 备用 |
| `assignees` | `[]int64` | `number[]` | ⚠️ 整数溢出风险（BigInt → Number） |
| `workspace_id` | `int64` | `number` | ⚠️ JS Number 精度 2^53-1 |
| 迭代进度饱和度 `saturation` | `numeric(8,2)` | `number` | ✅ |
| `version_id` (release) | BIGINT | `release_version_id?: number` | 🔴 字段命名建议统一 |
| `found_version_id` | BIGINT | 有 | ✅ |
| `fix_version_id` | BIGINT | 有 | ✅ |
| 新增字段 `regression_risk` | defect 表新增 | 前端 defect Interface 缺失 | 🔴 漂移 |

**建议**：

1. **大整数传输约定**：雪花 ID 超过 JS Number 安全范围时，后端通一出 string（或用 `BigInt` 前端处理）。当前雪花 ID 未补零到越界，但 64 位系统可能接近极限，建议 ID 字段统一出 string；
2. **字段命名统一**：`release_version_id` → `version_id`（已有 `found_version_id` / `fix_version_id`，应保持 `xxx_version_id` 模式）；
3. **差分检测脚本**：CI 中引入 swagger → typescript interface diff，自动检测前后端字段漂移。

---

#### 3.2.3 错误码未全量贯穿 —— P1

后端 `pkg/errs` 已建立 `AppError` envelope 体系（见 errs_constructors_test、errs_test），但：

- 不是所有 domain 包都使用了统一 `errs`（部分仍返回裸 `fmt.Errorf`）；
- 前端 `api/errors.ts` 的 `ApiError` 结构固定，对 domain-specific 错误详情提取不全；
- 错误码文档没有枚举中心注册表。

**建议**：

1. 建立 `pkg/errs/codes.go` 枚举中心（`CodeWorkspaceNotFound = "WORKSPACE_NOT_FOUND"`）；
2. 所有 domain 错误包装必须使用 `errs.New(domain, code, msg)`；
3. 前端拦截器按 `error.code` 匹配显示对应 type/i18n 文案。

---

#### 3.2.4 前端 E2E 覆盖缺口 —— P2

12 个 spec 覆盖了 auth/automation/comment/kanban/notification/search/security/version/workflow/workspace，但缺少：

- **国际化（i18n）切换全链路**：`LanguageSwitcher.vue` 存在但无对应测试；
- **视图偏好持久化**：`ViewsManager.vue` 操作无测试；
- **报表联动**：`DashboardView.vue` 卡片→详情跳转。

**建议**：新增 3-5 个 spec 补齐以上场景。

## 五、总结

Ydsz Plane 在架构成熟度方面确实达到了国内开源项目管理平台的**第一梯队**水平。当前最核心的三条主线是：

1. **数据库模型三表分立 vs 架构文档单表设计的矛盾**——这是最大的一次架构债务。单 `issues` 表统一后，代码复用率可提升 60%、新功能接入成本下降一半、跨类型联合查询从 UNION ALL 变为单表 WHERE type_code。建议作为 S18 的主线任务推进。

2. **后端测试 21.6% 文件覆盖率是最大质量风险**——特别是 38 文件的 `issue` 核心域只有 6 个测试文件。这一项如果投入 3-4 天补齐 IssueService 的 Create/Update/Transition 领域测试，就能消除 80% 的回归风险。

3. **前后端类型安全断裂**——手工维护 TS interface 不是长久之计。3-4 天补齐 swaggo 注解即可解锁 orval 全量生成，后续迭代中端到端类型安全零成本。

三条主线合计投入约 **2-3 人周**，即可将系统从「功能完整」推进到「质量可靠、类型安全、安全合规」的工程成熟度新阶段。
