## 三、安全加固（P0-P2）

### 3.1 SQL 注入残余风险消除 【P0】

**现状**：`coordinator.go` 中 `fmt.Sprintf` 拼接 SQL 语句（虽当前来自静态分析无法识别的枚举路径），`dialect.go:JSONBExtract` 使用 `fmt.Sprintf` 拼接字段名。

**对标**：OWASP A03:2021、阿里/美团安全编码规范强制参数化原则。

**建议**：

1. SQL 拼接处改用白名单映射 + switch statement 校验，拒绝非预期表名/字段名
2. dialect 层统一使用 `pgx.Identifier` 或 ` QuoteIdentifier` 转义
3. 引入 `go-sec-check` 或 Semgrep 规则 CI 门禁，引入即阻断

**预估工期**：1-2 天

---

### 3.2 OIDC Client Secret 加密存储 【P0】

**现状**：OIDC `client_secret` 明文入库，注释声明 AES-256-GCM 但未见实现。`pkg/crypto` 接口已存在但覆盖不完整。

**对标**：OWASP ASVS 2.11、等保三级密钥管理、Vault 实践。

**建议**：

1. `pkg/crypto.Cipher` 接口统一封装加密/解密，密钥由环境变量注入
2. `client_secret` 字段读取时自动解密，入库前自动加密
3. 密钥轮换：新旧密钥共存窗口期 = 当前 JWT 最大有效期，确保存量 token 可用
4. 添加启动时密钥连通性自检（encrypt → decrypt round-trip）

**预估工期**：1 天

---

### 3.3 Refresh Token 轮换与吊销 【P0】

**现状**：Refresh Token 无轮换机制，无 revoke 能力；失窃 refresh 可无限续期。

**对标**：OWASP ASVS 3.1、RFC 6749 §10.4、Google OAuth 2.0 for Mobile & Desktop Apps。

**建议**：

1. 实现 **refresh token 家族（family）轮换**：每次签发新 refresh token 记录 `family_id`，检测 reuse 立即吊销整族
2. Redis 维护 revocation list（TTL 与 token 过期对齐）
3. 提供用户可见的"活跃会话"管理页面（查看/吊销设备）
4. 管理员强制吊销接口（紧急情况）

**预估工期**：2-3 天

---

### 3.4 SAML 签名校验门控强化 【P1】

**现状**：`SkipSignature=true` 在配置层可能被误用，生产环境风险高。

**对标**：SAML 2.0 安全指南、等保三级。

**建议**：

1. 当 `SkipSignature=true` 时强制加环境变量 `SAML_DEV_ONLY=true` 门控
2. 生产构建直接编译拒绝（build tag 门控：`_production` 拒绝 `SkipSignature`）
3. 日志告警：SAML 响应未签名的 WARNING

**预估工期**：0.5 天

---

### 3.5 依赖项安全扫描 【P1】

**现状**：Go modules + npm 依赖，但无自动化安全扫描。

**对标**：Snyk、Dependabot、GitHub Dependabot alerts。

**建议**：

1. CI 集成 `govulncheck` + `npm audit`，发现高危 CVE 即阻断
2. 添加 `.github/dependabot.yml` 自动更新依赖
3. 定期 SBOM 生成（`syft` 或 `go mod graph` 导出）

**预估工期**：0.5 天

---

### 3.6 CSP / 安全响应头 【P2】

**现状**：基础安全头存在，但 CSP 策略可能未全覆盖。

**对标**：OWASP Secure Headers Project、Mozilla Observatory。

**建议**：

1. 强化 CSP 策略：`default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'`
2. 添加 `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`
3. HSTS 预加载列表申请（生产域名）
4. 添加 `/security.txt` 安全披露端点

**预估工期**：0.5 天

## 四、接口契约与测试

### 4.1 补全 swaggo 注解覆盖率 【P0】

**现状**：`docs/swagger/swagger.yaml` 仅覆盖认证/工作空间等基础端点；issue/sprint/version/automation 等 20 个核心域缺失。

**对标**：Stripe API 文档标准、GitHub API OpenAPI 规范。

**建议**：

1. 按域分批补全 `@Summary` `@Description` `@Param` `@Success` `@Failure` `@Router` 注解
2. 引入 `swaggo` 覆盖率门禁：`make swagger-coverage` 计算注解覆盖率，目标 ≥90%
3. 每个新 Controller 上线前必须带 swagger 注解

**预估工期**：2-3 天

### 4.2 Playwright E2E CI 真实运行 【P0】

**现状**：`web/e2e/` 已有 13 个 spec 覆盖 state-machine/webhook/安全/搜索/通知，但 CI 中未真实运行。

**对标**：项目 DoD 声称 "E2E 覆盖核心路径"。

**建议**：

1. 新增 Playwright CI job（复用 Go 测试的 postgres+redis 服务矩阵）
2. `main` 分支推送时运行，PR 选择性运行（label 触发）
3. 添加视觉回归：关键页面截图对比（storybook + playwright）
4. E2E 失败自动上传 trace（`npx playwright show-trace`）

**预估工期**：1-2 天

### 4.3 领域层 Mock 化集成测试 【P1】

**现状**：集成测试依赖真实 PG/Redis，领域层直接持有 `*pgxpool.Pool` 接口。S16 P0-2 Repository 接口已抽象，但 Mock 化测试未铺开。

**对标**：Uber Go Style Guide "Test Doubles"、Google SWE 测试金字塔。

2. Service 层单元测试使用 Mock Repository，无需真实 DB

4. 添加 `Test<DomainService>_<Method>_<Case>` 模式

**预估工期**：2-3 天

### 4.4 错误码注册表全量贯穿 【P1】

**现状**：错误 envelope 格式已定义但未全量贯穿；前端错误处理依赖手动解包。

**对标**：Microsoft REST API Guidelines、Google Cloud Error Model。

4. 每个 Controller 的错误码在 swagger 注解中声明

## 五、前后贯通与类型安全

### 5.1 OpenAPI TypeScript 类型生成流水线（深化）【P0】

**现状**：S16 P0-1 已引入 orval + openapi-typescript，但后端 swagger 注解不完整导致生成覆盖率受限。

**对标**：美团前端 API 类型生成规范、tRPC 端到端类型安全。

**建议**：

1. 先补全后端全量 swaggo 注解（见 4.1）
2. CI 加入 diff 检查：前端 `api/services/` 与后端 swagger 漂移即警告
3. 目标：前端调用后端时 0 手写类型，全部 orval 生成

**预估工期**：1-2 天（配合 4.1）

---

### 5.2 any 类型治理 【P1】

**现状**：非测试文件 98 处 `any`，集中在 `CommandPalette.vue`、`GlobalSearch.vue`、`FocusModeView.vue`；domain service 中 `Record<string, any>` 占主体。

**对标**：美团前端 TS 规范 `@typescript-eslint/no-explicit-any: error`、Total TypeScript。

**建议**：

1. ESLint 叠加 `@typescript-eslint/recommended-type-checked` 严格规则
2. `any` → `unknown` + 类型守卫迁移（分批进行，ratchet 只降不升）
3. 高频场景定义共享类型：`FilterParams`、`SortConfig`、`PaginationCursor`
4. CI 添加 any 计数 ratchet：`max_any_count: 50`（逐步收紧到 0）

**预估工期**：2-3 天

---

### 5.3 Zod / Valibot 运行时校验 【P1】

**现状**：前端表单校验依赖 Element Plus `rules`，后端 validator 使用 `go-playground/validator`，前后端校验逻辑不同步。

**对标**：tRPC + Zod、Next.js Server Actions + Zod。

**建议**：

1. 共享校验 schema：后端用 Go validator 标签，前端用 Zod/Valibot（通过 orval 生成）
2. 关键字段（email/URL/identifier）的校验规则前后端同源
3. 复杂业务规则（状态流转、必填字段）运行时 schema 校验

**预估工期**：1-2 天

---

### 5.4 API 客户端拦截器增强 【P1】

**现状**：`web/src/api/client.ts` 已实现基础拦截（X-Request-ID、401 刷新、429 限流），但缺少请求去重、乐观更新、离线队列。

**对标**：TanStack Query（React Vue 版 Vue Query）、Apollo Client。

**建议**：

1. 引入 `@tanstack/vue-query`：自动缓存、失效、窗口焦点刷新、重试
2. 乐观更新：看板拖拽后立即更新本地缓存，失败回滚
3. 离线队列：网络恢复后自动重放 failed mutations
4. 请求去重：同一查询 5s 内合并为单次请求（singleflight）

**预估工期**：2-3 天

## 六、性能与缓存

### 6.1 BatchUpdate 事务包裹与 Saga 补偿 【P0】

**现状**：S16 P0-3 BatchUpdateV2 优化 DB 往返，但每个 ID 单独事务，部分失败时态不一致。

**对标**：阿里《Java/Go 规范》事务边界最小化但保证一致。

**建议**：

1. 批量操作加整体事务包裹（单事务 ≤100 条 SQL，避免长事务）
2. 失败详细日志：逐条记录失败原因，返回 200 + `results[].status` 明细
3. 大批量（>500 条）拆分为多个子事务，失败部分回滚
4. 引入 Saga 补偿模式（独立回滚记录表）处理跨聚合操作

**预估工期**：1-2 天

---

### 6.2 ES Reindex 并行化 【P0】

**现状**：`es/client.go` 蓝绿 Reindex 为单线程 channel 读 + 内存 batch，百万级工作项下易成瓶颈。

**对标**：Elasticsearch 官方 bulk 最佳实践、字节 ES 并行写入规范。

**建议**：

1. 改为 worker pool parallel bulk（按 `workspace_id` hash 分区）
2. 动态 worker 数量：`min(CPU*2, 16)`
3. bulk size 自适应：根据响应时间调整（2000→5000→10000）
4. 进度可观测：`plane_reindex_progress{width, total, processed}` 指标

**预估工期**：1-2 天

---

### 6.3 Outbox Relay 事件驱动唤醒 【P1】

**现状**：`events/outbox.go` Relay 周期性 500ms 轮询，冷启动/低事件时仍空转 12% CPU。

**对标**：Google SRE 降低无效负载、PostgreSQL LISTEN/NOTIFY 模式。

**建议**：

1. 引入 Redis Pub/Write-ahead 唤醒信号：写入 Outbox 同时 `PUBLISH outbox:new_event`
2. Relay 改为"有事件时立即唤醒 + 空闲时 5s 兜底轮询"
3. 实现 `LISTEN/NOTIFY` 备选方案（无 Redis 部署场景）
4. 监控指标：`plane_outbox_poll_wake_total{source=pubsub|timer}`

**预估工期**：1 天

---

### 6.4 Redis 能力封装与连接池指标 【P1】

**现状**：`cache/redis.go` 仅有 `NewClient`，Pub/Sub、分布式锁、滑动窗口限流器未落地；`persistence/pgxpool` 缺少指标。

**对标**：12-Factor 缓存最佳实践、Prometheus 规范。

**建议**：

1. 封装 `cache` 子包：`Lock`（Redlock）、`PubSub`、`RateLimiter`（滑动窗口）、`LeaderElection`
2. 连接池指标导出：`plane_pg_pool_acquire_duration_seconds`、`plane_redis_commands_total`
3. 限流细粒度：按用户/按 IP/按端点三级限流（已有基础，需完善）
4. 缓存策略抽象：`CacheAside`、`WriteBehind`、`ReadThrough` 模式封装

**预估工期**：2-3 天

---

### 6.5 批量写入使用 pgx.CopyFrom 【P1】

**现状**：seed-scale 脚本和批量操作仍用逐条 INSERT，pgx.CopyFrom 能力未利用。

**对标**：pgx 官方 COPY 协议最佳实践。

**建议**：

1. 批量创建（导入/seed）使用 `pgx.CopyFrom`，吞吐提升 5-10 倍
2. 批量更新使用 `unnest` 存储过程：`WHERE id = ANY($1)` + `SET field = data.field FROM unnest`
3. 埋点对比：批量操作耗时 vs 记录数曲线

**预估工期**：1 天

---

### 6.6 前端路由懒加载与代码分割 【P1】

**现状**：路由已 lazy 加载，但 `manualChunks` 已清理（S16 P1-1 验证通过），仍可优化。

## 十四、总结

Ydsz Plane 已经是国内开源项目管理平台中的**架构标杆**，具有以下差异化优势：

1. **信创合规独家**：国密 SM2/SM3/SM4 + 达梦/人大金仓适配
2. **架构成熟度高**：Outbox 事件驱动、RLS 行级安全、蓝绿 Reindex
3. **工程规范完善**：96 条 AI 编码规范、CI 门禁、测试金字塔
4. **功能覆盖全面**：需求/任务/缺陷/迭代/版本/看板/仪表盘/自动化/搜索

**主要差距**（对标 Jira/Linear）：

1. 搜索深度（缺 AI 语义搜索和 Completion Suggester）
2. 自动化可视化（缺拖拽规则构建器）
3. 集成生态（缺集成市场）
4. 移动端体验（缺原生 App/PWA）

**建议优先执行**：3.1 SQL 注入 → 3.2 OIDC Secret → 4.2 E2E CI → 6.3 Outbox 唤醒 → 8.1 Completion Suggester → 11.1 大屏驾驶舱 → 10.1 OpenTelemetry → 7.1 issue 模块拆分。

预计 6-8 周可完成 P0+P1 高价值项，将产品成熟度从"Jira Cloud 的 75%"提升到"Jira Cloud 的 85%+Linear 的 70%"。
