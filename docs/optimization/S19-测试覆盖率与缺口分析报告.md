## 7. 可落地的改进建议

### 7.1 短期（本周）— 启用 dockertesthelper

验证冒烟测试：

```
go test -tags dockertest -run TestSmoke ./internal/testing/dockertesthelper/...
```

完成后即可将 dockertesthelper + txfixture 作为所有 handler/service 集成测试的标准基座。

### 7.2 短期（本周）— 复制 ai/handler_test.go 模式

`internal/application/ai/handler_test.go` 是项目中唯一完成 handler 层测试的文件，核心模式：

- `httptest.NewRecorder` + `http.NewRequest` 发起请求
- 断言 HTTP 状态码和 JSON 响应体

可作为模板推广到以下文件（每个文件对应创建 `*_handler_test.go`）：

## 8. 总结

### 已取得的成果

- 项目核心 issue 模块的领域模型、纯函数、HTML/评论清洗有较为充分的测试覆盖（76 个测试函数）
- automation 引擎的 SPI 接口（`ExecutionContextProvider`、`ActionExecutor`）设计利于单元测试
- dockertesthelper + txfixture 集成测试基础设施完整，只差依赖安装
- 至少 1 个 handler 测试最佳实践（`ai/handler_test.go`）可供复制

### 主要风险

1. **核心工单 CRUD handler（2560 行 / 64 函数）零测试** — 任何回归都只能靠手动验证
2. **工作空间 Create/Get/Update/Archive 核心事务方法零测试** — 直接影响租户生命周期
3. **自动化引擎的 EvaluateEvent 链路零测试** — 关键事件驱动路径无守护
4. **OIDC / SAML 身份认证 1443 行零测试** — 安全敏感代码无法回归验证
5. **testcontainers-go 尚未安装** — 集成测试基座空有其名，所有 DB 依赖型 Service 测试无法落地

### 一句话建议

> **优先启用 dockertesthelper → 补齐 P0（issue handler + workspace service + automation engine）→ 复制 ai/handler 模式推广 handler 测试 → 引入 mockgen 和覆盖率门禁。**
