## 一、严重缺陷（按影响排序，均已在源码中逐行核实）

### 🔴 CRITICAL-1：租户隔离（RLS）与 Go 代码结构性矛盾

**位置**：`sql/ydsz-plane-init.sql:6603-6636` + `internal/application/issue/issue_service.go:180`

- SQL 侧：对 **38 张表**启用 RLS，策略为 `workspace_id::text = current_setting('app.workspace_id', true)`
- Go 侧：只有少数 `withTx` 写路径调用 `set_config('app.workspace_id', ...)`（issue_service.go:823、timelog_service.go:216、executor.go:288、project_init.go:40）
- **所有直连接池的读路径**（`IssueService.GetByID` 192 行、`List`、`CommentService.ListByIssue`、relation 的 `hasCycle` 等）**从不设置该 GUC**

**后果（二选一，均不可接受）**：
1. RLS 生效 → 未设置 GUC 的查询 `workspace_id = NULL` 恒假 → **核心读接口全部返回空集，应用瘫痪**
2. RLS 未生效（部署时跳过）→ 所有 `WHERE workspace_id=$1` 之外的查询成为**跨租户读取**（如 comment_service.go:195 仅 `WHERE c.issue_id=$1`）

### 🔴 CRITICAL-2：Issue 乐观锁失效（丢失更新）

**位置**：`internal/application/issue/issue_service.go:1197-1270` `buildUpdateSet`

- 该函数构造的 UPDATE SET 子句**没有 `version = version + 1`**
- 对比 476 行（Transition）与 606 行（directUpdateIssue）都有自增 —— **说明是遗漏而非设计**
- 场景：A/B 同时读到 version=5，各自 `WHERE version=5` 更新均成功（version 从未变过）→ 后写覆盖先写，**丢失更新**
- 附带问题：`args` 中 `in.Version` 由**客户端传入**，`verIdx` 等 3 个变量赋值后 `_ =` 丢弃（357-360 行死代码）

### 🔴 CRITICAL-3：Sprint 复盘快照恒为全零

**位置**：`internal/application/sprint/sprint_service.go:332-395`

- `Complete` 先调用 `handleUnfinishedTx`（343-346 行）**DELETE 清空 `sprint_issues`**
- 之后才调用 `computeReview`（349 行）统计 `sprint_issues` —— **此时表已空**
- 后果：Committed/Completed/Joined 全部为 0；燃尽图、速率统计、容量建议全部输出空
- 附带：`UnfinishedNextSprint` 分支（392-394 行）只 DELETE、**从不 INSERT 到目标迭代** —— 未完成任务被静默丢弃回 backlog，注释声称的"迁移"未实现；`UnfinishedKeep` 与 `UnfinishedBacklog` 代码完全相同

### 🔴 CRITICAL-4：OIDC 引用不存在的表（运行即崩）

**位置**：`internal/application/auth/oidc.go:113,208,213,488` + `sql/ydsz-plane-init.sql`

- 代码读写 `sso_sessions` / `sso_links` / `sso_providers` 三张表
- **schema 中这三张表完全不存在**（`grep -c "CREATE TABLE.*sso"` → 0）
- 任何 OIDC 调用 → `relation "sso_sessions" does not exist` 500
- 附带：`code_verifier` 被塞进 `error_message` 列（oidc.go:120-123），属明显 hack

### 🔴 CRITICAL-5：搜索相关性排序/高亮参数错位

**位置**：`internal/application/search/service.go:193-208`

- `args = []interface{}{q.WorkspaceID}` → `$1 = workspace_id`，tsQuery 是 `$2`
- 但 `ts_headline(...to_tsquery('simple', $1)...)` 与 `ts_rank(..., to_tsquery('simple', $1))` 都引用 `$1`
- **后果：用 workspace_id 当搜索词做相关性打分和高亮** —— 排序基本失效，高亮乱标

### 🟠 HIGH-6：存储型 XSS 缺口（工作项描述未净化）

**位置**：`internal/application/issue/html_sanitize.go` + `issue_service.go:659,1165`

- `SanitizeHTML()` 只接入了**评论**（handler.go:1101,1144）
- `createIssue`/`updateIssue` 的 `DescriptionHTML` **原样落库**（issue_service.go:659,1165），从未净化
- 前端 `v-html` 渲染时若未二次净化 → **存储型 XSS**

### 🟠 HIGH-7：基础设施层真实缺陷（已逐行核实）

## 三、修复优先级（代码级）

### 第一批：数据正确性 & 安全（P0，先于一切功能开发）

1. **RLS 矛盾** —— 决策：要么统一所有读路径走 `withTx`（性能差），要么改为连接池 `pgx.ConnConfig.AfterConnect` 每连接默认设置 GUC（推荐，对齐字节/腾讯多租户实践）
2. **Issue 乐观锁** —— `buildUpdateSet` 追加 `version = version + 1`，并去掉 `in.Version` 客户端传入
3. **Sprint 复盘全零** —— 调整顺序：先 `computeReview` 后 `handleUnfinishedTx`；补全 `NextSprint` 迁移 INSERT
4. **搜索参数错位** —— ts_rank/ts_headline 改用 `$2`（搜索词索引）
5. **工作项描述 XSS** —— createIssue/updateIssue 的 DescriptionHTML 接入 `SanitizeHTML`
6. **OIDC** —— 要么建表落地，要么删文件（当前状态是"运行即崩"的假功能）

### 第二批：基础设施可靠性（P1）

7. mq：NotifyPublish 注册移出循环；Nack 改 false 并接 DLQ；修 DLQ 路由键；延迟队列用真实 DLX 回环
8. ws：pubsub 生命周期移出 handler defer；广播加 send 保护（select+closed chan）；upgrader 改为每 Hub 实例
9. events：批处理改事务或逐条幂等
10. persistence：达梦 Upsert 真实现或显式 error
11. metrics：补 singleflight、接 InvalidateProject、修 LastPoints
12. automation：修 resolveField 支持模板字段；补 webhook 动作或显式报错

### 第三批：功能完整性（P2）

13. 活动日志接入 issue 域调用
14. 状态机通配符规则入库
15. Refresh token 轮换存储（Redis 令牌族）
16. 事件源补全（issue.assigned 等）
17. intake IP 限流 + captcha 校验
18. webhook 手动重投真实现
