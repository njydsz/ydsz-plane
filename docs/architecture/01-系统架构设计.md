## 1. 架构目标与约束

### 1.1 业务目标
打造面向中国软件团队的开源、自托管项目管理平台，核心域为 **工作空间 → 项目 → 工作项（需求/任务/缺陷）**，辅以迭代、版本日、仪表盘、工作台、搜索、通知、Webhook、自动化、效能度量等增强能力。

### 1.2 技术约束（来自 README/PRD，作为既定决策）

| 层次 | 选型 | 备注 |
|------|------|------|
| 后端 | Go 1.26.5 / Gin 1.12 | 单体模块化（Modular Monolith），微服务就绪 | |
| 前端 | Vue 3.5 + TS + Vite 6 + Element Plus + Pinia | 视觉层对齐 Plane 设计语言 |
| 数据库 | PostgreSQL 16 | 信创适配层预留达梦/人大金仓方言 |
| 缓存 | Redis 7 | 缓存 + 分布式锁 + 限流 |
| 搜索 | Elasticsearch 8 | 全局搜索、知识库全文检索 |
| 对象存储 | MinIO / S3 | 附件、Logo、封面 |
| 异步/事件 | Redis Streams（事件总线）+ Asynq（任务队列） | Outbox 投递替代 NATS JetStream；Asynq 替代 Python Celery |
| 部署 | Docker Compose（一键）/ Helm（可选） | |

### 1.3 性能与非功能目标
- API P95 ≤ 200ms，页面加载 P95 ≤ 2s
- 单项目工作项 ≥ 100 万，并发用户 ≥ 1000
- SLA ≥ 99.9%，等保三级基线，信创兼容

## 2. 总体架构

### 2.1 架构形态：模块化单体 + 异步工作进程

0→1 阶段**不做微服务拆分**。采用单代码库、单部署单元的模块化单体（Modular Monolith），模块边界按 DDD 限界上下文划分，模块间只允许通过 Application Service 接口与领域事件通信，为将来拆服务预留接缝。


### 2.2 关键架构决策（ADR 摘要）

| # | 决策 | 结论 | 理由 |
|---|------|------|------|
| ADR-1 | 单体 vs 微服务 | 模块化单体 + 独立 worker 进程 | 0→1 阶段交付速度优先；事件驱动保证可拆分性 |
| ADR-2 | 多租户隔离（PRD 开放问题①） | **共享 Schema + workspace_id + PostgreSQL RLS** | Schema-per-tenant 运维成本高（迁移×N）；RLS 提供数据库级兜底隔离，应用层 TenantMiddleware 强制注入租户上下文 |
| ADR-3 | 工作项建模 | 单表 `issue` + `type` 区分需求/任务/缺陷 | PRD 既定；类型差异字段用类型化 JSONB `type_attrs` + 列存高频过滤字段（severity 等） |
| ADR-4 | 事件机制 | **Transactional Outbox → Redis Streams** | 保证"写库成功事件必达"；worker 消费幂等；替代 NATS JetStream，降低运维复杂度 |
| ADR-5 | 自动化引擎 | 规则存 JSON DSL，执行走 Asynq 任务（非 Celery） | Go 技术栈对齐；规则编译为可序列化执行计划 |
| ADR-6 | 实时推送 | WSS（WebSocket）直连 api 服务，Redis Pub/Sub 扇出 | 站内通知、看板协同刷新 |
| ADR-7 | 全文检索 | ES 异步双写（事件驱动），DB 为唯一事实源 | 允许 ES 重建索引 |
| ADR-8 | 富文本 | 存 `description_json`（结构化）+ 派生 `description_html` / `stripped` | 编辑器选型 TipTap（Vue3 生态成熟，贴近 Plane editor 体验） |

## 3. 领域模型

### 3.1 限界上下文划分

| 上下文 | 核心聚合 | 职责 |
|--------|----------|------|
| iam | User, ApiToken, Session | 认证、用户、令牌 |
| workspace | Workspace, WorkspaceMember, Invitation | 租户、成员、角色、邀请 |
| project | Project, ProjectMember, Module, Label, State, EstimatePoint | 项目配置、模块（归档属性）、状态机配置、标签 |
| issue | Issue, IssueRelation, IssueDependency, IssueComment, IssueActivity, TimeLog, IssueTemplate | 需求/任务/缺陷统一聚合，WBS、依赖、工时、活动日志 |
| sprint | Sprint, SprintIssue, SprintSnapshot | 迭代生命周期、燃尽快照 |
| version | Version, VersionSprint, Checklist | 版本日聚合、Release Notes、交付报告 |
| intake | IntakeChannel, IntakeIssue | 收件箱与转正 |
| doc | Document, DocumentVersion, DocumentLink | 项目文档归档 |
| kb | KnowledgeSpace, KnowledgePage, PageVersion, PageRelation | 知识库 |
| notification | Notification, Subscription, Digest | 通知编排与投递 |
| search | SearchQuery, SearchHistory | 查询语法解析（索引在 ES） |
| automation | AutomationRule, RuleExecution | TCA 规则引擎 |
| webhook | Webhook, WebhookLog | 外向集成 |
| bi | DashboardConfig, Widget, MetricSnapshot | 仪表盘与效能度量 |

### 3.2 核心聚合：Issue

```
Issue（聚合根）
├── id / project_id / sequence_id（项目内自增 → IDENTIFIER-123）
├── type: requirement | task | defect        ← 由 IssueType 决定
├── parent_id（WBS，限三级，同类型内嵌套）
├── name / description_json / description_html / description_stripped
├── state_id → State（group: backlog/unstarted/started/completed/cancelled/triage）
├── priority: urgent/high/medium/low/none
├── ── 类型差异字段（defect 专有，独立列便于过滤）──
├── severity: 1..5（P0 必补）
├── found_phase / found_version_id / fix_version_id
├── root_cause_category / verifier_id / environment(JSONB)
├── ── 任务工时（task 专有）──
├── actual_effort / remaining_effort / delay_reason / category
├── ── 通用 ──
├── start_date / target_date / completed_at / is_draft / progress（冗余，由子项完成率回写）
├── module_ids(M2M) / label_ids(M2M) / assignee_ids(M2M) / watcher_ids(M2M, P1)
├── sprint_id / version_id（需求/任务首次发布版本）
└── source（需求来源, P1）
```

**不变量（Domain Invariants）**：
1. WBS 层级 ≤ 3 层，且父子必须同 type；禁止循环父链。
2. 需求拆解不产生任务；需求↔任务仅通过 `IssueRelation(implemented_by/relates_to...)` 关联。
3. 缺陷可同时关联需求与任务（IssueRelation），且必有 severity；解决时必填 root_cause_category。
4. 同一工作项不得同时处于两个 active Sprint（可配置开关）。
5. 状态流转必须经过 State 配置的流转规则（缺陷默认状态机：新建→确认→处理中→修复→待验→关闭/拒绝/重开）。
6. 删除一律软删除（deleted_at），回收站 30 天。

### 3.3 版本日—迭代模型
- `Version 1─N Sprint`（version_sprint 关联表）；Sprint 可独立存在。
- Issue.version_id = 首次发布版本（唯一）；Issue.sprint_id 可随排期变化。
- 版本日进度 = 聚合各 Sprint 完成度；发布时生成 Release Notes（模板渲染）+ 交付报告（由 bi 上下文计算）。

### 3.4 状态机设计
- State 按 project 维度配置，`group` 决定统计口径，`sequence` 决定看板列序。
- 流转规则表 `state_transition`（from_state, to_state, required_fields[], allowed_roles[]）——0→1 阶段先内置三组模板（开发流/缺陷流/需求评审流），自定义流转规则放 Phase 3 与自动化引擎打通。

### 4.2 租户隔离落地（ADR-2）
- 所有业务表带 `workspace_id` 冗余列（含 project 子表），建复合索引前缀。
- 启用 RLS：`CREATE POLICY tenant_iso ON issues USING (workspace_id = current_setting('app.workspace_id')::bigint);`
- 请求入口中间件解析 workspace slug → 在连接上 `SET LOCAL app.workspace_id`，事务内生效。
- 信创适配：SQL 层通过方言接口抽象（`internal/infrastructure/persistence/dialect`），达梦/金仓仅替换驱动与少量函数。

### 4.4 检索设计（ES）
- 单索引 `ydsz_issues`（按 workspace routing）+ `ydsz_pages`（知识库）+ `ydsz_docs`。

- 同步链路：domain_events → worker → bulk index；提供 `make reindex` 全量重建。

## 5. API 设计规范

- 风格：REST + 统一 envelope；版本前缀 `/api/v1`。
- URL 形如：`/api/v1/workspaces/{slug}/projects/{identifier}/issues/{sequence_id}`。
- 认证：Session（Web）/ API Token（`X-Api-Key`）/ OAuth2（Phase 3 SSO）。
- 分页：`?cursor=`（默认，无限流列表）与 `?page=&per_page=`（报表类）。
- 过滤：`?state__group=started&priority__in=urgent,high&assignee=me`（字段__操作符约定）。
- 字段裁剪：`?fields=id,name,state`。
- 错误格式：`{"error":{"code":"ISSUE.INVALID_STATE_TRANSITION","message":"...","details":{}}}`，HTTP 语义化状态码。
- 幂等：写操作支持 `Idempotency-Key` 头（Redis 去重 24h）。
- 限流：默认 100 req/min/用户，登录接口 10 req/min/IP。
- OpenAPI 3.0 由代码注解生成（swaggo），Swagger UI 挂在 `/api/docs`。

## 6. 前端架构（对齐 Plane 界面风格）

### 6.1 视觉语言映射（Plane → Vue/Element Plus）

Plane 的界面特征（来自 `D:\Code\github\Plane` 参考）：
- 三段式布局：左侧可折叠工作空间侧边栏 + 顶部项目页头 + 内容区；
- 设计令牌驱动的主题系统（CSS 变量，`data-theme` 切换亮/暗）；
- 极简中性色 + 单一品牌强调色；卡片化、低边框、弱阴影；
- 全局命令面板（Ctrl/Cmd+K，power-k）；快捷键体系；
- 看板/列表/日历/甘特多视图切换，视图偏好随用户保存。

落地方式：
- **保留 Element Plus 组件能力，但用设计令牌覆盖主题**：建立 `packages/design-tokens`（CSS 变量层，映射 Plane 的 surface/primary/placeholder 语义），通过 `el-config-provider` + SCSS 变量注入，使 EP 组件呈现 Plane 式观感。
- 自建基础组件层 `packages/ui`（Button/Dropdown/Popover/Modal/Avatar/Badge/Card/EmptyState/ContextMenu），对 EP 做门面封装，页面层只依赖 ui 包，便于将来换库。
- 编辑器选型 **TipTap 3**（Vue 集成成熟，体验贴近 Plane editor），产出 `description_json`。

### 6.3 状态与数据流
- Pinia 按域分 store；服务端数据用 **TanStack Query (Vue Query)** 管理缓存/失效，避免手写 loading 态。
- 实时：单例 `ws-client`，订阅 `workspace:{id}` 频道，收到事件后精确失效对应 Query Key（看板协同不整页刷新）。
- 命令面板（Ctrl+K）：跳转 + 创建 + 搜索建议三类命令源，复用全局搜索 API。

### 6.4 关键页面与路由

```

/:workspaceSlug/projects/:ident/issues/:seq    → 工作项详情
/:workspaceSlug/projects/:ident/sprints/:id    → 迭代详情（燃尽/站会模式）
/:workspaceSlug/projects/:ident/versions/:id   → 版本日聚合视图
/:workspaceSlug/projects/:ident/dashboard      → 项目仪表盘（可配置卡片）
/:workspaceSlug/projects/:ident/intake|docs|modules|settings
/:workspaceSlug/kb/:spaceSlug/...              → 知识库
/search                                           → 全局搜索（Ctrl+K 入口）
```

## 7. 横切关注

### 7.1 事件流（Outbox → Redis Streams → Worker）

事件类型（与 Webhook 事件对齐）：
`issue.created/updated/deleted/status_changed`、`sprint.started/completed`、`version.released`、`member.added/role_changed`、`comment.created`、`automation.executed/failed` 等 30+。

投递语义：at-least-once；消费者幂等键 = `event_id`。
扇出消费者：notification-dispatcher / es-indexer / webhook-dispatcher / automation-evaluator / metrics-recorder / ws-fanout。

### 7.2 自动化引擎
- 规则 = Trigger（事件/Cron）+ Conditions（字段表达式树）+ Actions（≤10，transition/assign/notify/create/webhook/copy_field）。
- 执行：事件到达 → 匹配规则 → 生成 Asynq 任务（同 issue 串行队列，防竞争）→ 执行并落 `rule_executions`；连续失败 3 次自动禁用并告警。
- Cron 触发器由 Asynq Scheduler 承载。

### 7.3 效能度量（bi）
- 离线计算：每日 01:00 聚合任务生成 `metric_snapshots`（按 project/sprint/version 粒度）；DORA 数据依赖 Webhook 接收 CI/CD 部署事件。
- 仪表盘卡片：实时类直查 DB（带缓存），趋势类读快照表。

### 7.4 安全
- 认证：bcrypt 密码、JWT(access 15m + refresh 30d)、可选 TOTP（P2）。
- 授权：RBAC 双层（workspace 角色 + project 角色）+ 资源级校验中间件；权限矩阵以 PRD §8.1.4.3 为准。
- 审计：管理类操作全量写 `audit_logs`。
- 传输/存储：HTTPS、附件私有桶 + 预签名 URL、Token 仅存 hash。
- 国密：TLS/存储加密抽象 `pkg/crypto` 接口，SM2/SM3/SM4 实现作为信创构建变体（build tag）。
- 防护：CORS/CSP 头、参数化查询、限流、Web hook HMAC-SHA256 签名。

### 7.5 可观测性
- 日志：zap 结构化日志，request_id 贯穿；ELK 收集。
- 指标：Prometheus（QPS/延迟/队列积压/WS 连接数）+ Grafana 预置面板。
- 追踪：OpenTelemetry（Gin/HTTP/DB/SQL 埋点），Jaeger 可选。
- 健康检查：`/healthz` `/readyz`（含 PG/Redis/ES 依赖探针）。

## 8. 部署架构

```
docker-compose.yml
├── nginx        (80/443, 静态资源+反代+限流)
├── web          (vite build 产物 → 由 nginx serve)
├── api          (Go 二进制, 无状态, 可水平扩展)
├── worker       (同一镜像, cmd/worker)
├── postgres:16  (卷持久化, 备份脚本)
├── redis:7
├── elasticsearch:8 (单节点, 可选 profile)
├── minio        (可选 profile, 默认本地磁盘卷)
└── nats
```
- 单命令 `docker compose up -d` 起核心栈；`--profile full` 加 ES/MinIO。
- K8s：提供 Helm Chart（Phase 3），HPA 基于 CPU/自定义指标。
- 信创交付：openEuler/麒麟 base 镜像 + ARM64 多架构构建。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 单表 issue 类型字段膨胀 | 查询/维护复杂度 | 高频过滤字段独立列 + 其余 JSONB；约束在应用层按类型校验 |
| RLS 与连接池配合 | 租户串扰 | 强制事务内 `SET LOCAL`；中间件统一获取/归还连接；集成测试覆盖 |

| 甘特/CFD 等重前端视图 | 工期 | 视图分 P1/P2 排期；P0 只看板/列表 |
| PRD 开放问题未决（IM 原生 bot、测试用例管理） | 范围蔓延 | 0→1 仅 Webhook 通道；测试用例管理明确不做（对接外部） |
