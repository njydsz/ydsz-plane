## 1. Webhook

### 1.1 事件目录（与 domain_events 对齐，JSON Schema 存 `api/events/`）

```
issue.created | issue.updated | issue.deleted | issue.status_changed | issue.commented
sprint.created | sprint.started | sprint.completed | sprint.deleted
version.created | version.updated | version.released
member.added | member.removed | member.role_changed
intake.submitted | intake.converted
automation.executed | automation.failed
deployment.recorded          -- DORA 内部事件也可外发
```

### 1.2 投递规格

```http
POST <target_url>
Content-Type: application/json
X-Ydsz-Event: issue.status_changed
X-Ydsz-Delivery: 01J2X8...            -- 投递唯一 ID（接收方幂等）
X-Ydsz-Signature-256: sha256=<hmac>   -- HMAC(secret, timestamp + "." + body)
X-Ydsz-Timestamp: 1786033228

{ "event": "issue.status_changed", "workspace": "acme", "project": "YD",
  "data": { "issue": {...}, "changes": {"state": {"from": "Todo", "to": "In Progress"}} },
  "actor": {...}, "occurred_at": "..." }
```

- 重试：5xx/429/超时(10s) → 退避 1min/5min/30min，共 3 次；最终失败标记 webhook `unhealthy` 并通知创建者。
- 防重放：接收方校验 timestamp ±5min。
- 日志：request/response/耗时存 `webhook_logs`（分区表，30 天）；管理页支持手动重投。
- 测试模式：管理页"发送测试事件"（合成 ping 事件）。
- SSRF 防护：URL 白名单协议（https 优先），解析后校验目标 IP 非内网/保留段。

## 3. 收件箱（Intake）

### 3.1 通道与提交

```
intake_channels: portal_slug（公开 URL /intake/{slug}）、is_public、
                 default_issue_type、auto_assign_rules JSONB
                 [{ "match": {"keyword": "支付"}, "assign_to": 123 }]
intake_issues:  tracking_id（YD-IN-XXXX，提交回执）、submitter_*、
                status[open|accepted|rejected|archived]、converted_issue_id
```

- 公开门户：免登录提交（限流 20/min/IP + 行为验证码）；附件走预签名直传。
- 提交者跟踪：`/intake/track/{tracking_id}` + 邮箱校验码，查看处理状态（只读视图，脱敏）。

### 3.2 转正流程

```
open ──管理员审核──▶ accepted（选择类型 requirement|defect）
                        │  1. 创建正式需求/任务/缺陷（标题/描述/附件复制）
                        │  2. intake.converted_issue_id 关联
                        │  3. 状态同步：正式 issue completed → intake=accepted+通知提交者
     └──▶ rejected（填写原因，通知提交者）
     └──▶ archived（暂不处理）
```

- 自动分配：按 auto_assign_rules 顺序匹配（关键词/类型），命中即指派 + 通知。
- 重复检测（P2）：提交时用 ES `more_like_this` 返回候选 Top5 提示。

## 4. 自动化引擎

### 4.1 规则 DSL（JSON，存 automation_rules）

```json
{
  "name": "缺陷修复自动指派验证人",
  "trigger": { "type": "issue.status_changed",
               "filter": { "type_code": "defect", "to_group": "started" } },
  "conditions": { "all": [
      { "field": "severity", "op": "<=", "value": 2 },
      { "field": "verifier", "op": "is_empty" }
  ]},
  "actions": [
    { "type": "assign", "field": "verifier", "value": "${issue.created_by}" },
    { "type": "notify", "channel": "in_app", "target": "${issue.created_by}",
      "template": "缺陷 {{issue.identifier}} 待你验证" }
  ]
}
```

- **Trigger**：`issue.created / issue.updated / issue.status_changed / issue.commented / sprint.completed / version.released / scheduled(cron)`
- **Condition**：`all/any` 嵌套；op：`eq/ne/in/gt/gte/lt/lte/contains/is_empty/changed`；`${...}` 变量引用上下文。
- **Action**（≤10 个，顺序执行）：`transition / assign / update_field / notify / create_issue / copy_field / webhook_call`。
- 内置模板 7 条（PRD §9.7）：子项全完成→父项完成、逾期提醒、版本发布→流转需求/任务/缺陷、Epic 点数汇总、In Progress→填开始日期、最闲人自动指派、新缺陷通知 Tech Lead。

### 4.2 执行引擎

```
事件到达 → 规则匹配器（按 project+trigger 索引）
  → 条件求值（纯函数，无 IO）
  → 生成 Asynq 任务（queue=automation:{project}，同 issue 串行：task_id=rule+issue 去重）
  → Action 执行器（仅调用 Application Service，不直连 DB）
  → rule_executions 落审计（status/duration/results）
  → 连续失败 3 次：禁用规则 + 通知 admin
```

- 并发控制：同一 issue 的规则执行经 Redis 锁串行化。
- 手动测试：规则编辑页"试运行"——对指定 issue 干跑（dry-run），返回匹配/将执行动作列表，不落库。
- 防循环：执行链路深度 ≤5（自动化触发的变更事件带 `via_automation=true` 标记，深度超限丢弃并告警）。
