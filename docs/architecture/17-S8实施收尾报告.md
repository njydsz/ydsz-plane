## 二、关键修复

### P0-1 迁移体系破坏（commit 94b4b9a 引入）

- **背景**：94b4b9a 删除全部 27 个增量迁移（0001–0027），替换为 Navicat 全量 dump `ydsz-plane-init.sql`；但 `cmd/migrate` 仍用 golang-migrate 读 `file://sql`，**迁移命令完全失效**，新环境无法建库。
- **决策**：按用户确认保留全量 dump 模式。改造 `cmd/migrate` 为双模式自动探测：
  - 存在 `NNNN_*.up.sql` → golang-migrate（保留增量能力）；
  - 仅有 dump → 全量初始化：单事务原子执行（失败全回滚，无半初始化状态）+ `ydsz_dump_state` 状态表幂等 + `version` 查询。
- **验证**（Docker PG 18 全新库实测）：`migrate up` 192ms 完成建库；重复执行幂等跳过；`migrate version` 正确回显。

### P0-2 搜索索引 P0 缺陷在 dump 中回退（联动 94b4b9a）

- **根因**：dump 里的 `fn_refresh_search_document` 只有 `issues` 分支，sprints/versions 从不被自动索引（对应 4321bd7 已修缺陷被回退）；且**单函数三分支写法本身有缺陷**——PL/pgSQL 从 sprints 表触发时解析 `NEW.sequence_id` 字段不存在直接报错（原 0027 方案从未实际应用，缺陷未暴露）。
- **修复**：按表拆分专用函数 `fn_refresh_search_document`（issues）/ `fn_refresh_sprint_search_document` / `fn_refresh_version_search_document`，每个函数仅引用自身表字段；`fn_cleanup_search_document` 保留 TG_TABLE_NAME 三分支（仅用 OLD/TG 元数据，安全）；为 sprints/versions 补建 4 个 AFTER 触发器。
- **验证**（全新库实测）：插入 issue/sprint/version 三类对象 → `search_documents` 全部自动索引；sprint 改名 → 索引同步更新；全文检索 `alpha:*` 命中；软删除 sprint → 索引清理。✅

### P0-4 索引一致性对账脚本（8.10）

- 交付 `scripts/reconcile-search`：逐 workspace 在租户上下文事务内对比 `search_documents` 与源表（issues/sprints/versions），输出**缺失**（源有索引无）与**孤儿**（索引有源无）两类漂移。
- `--fix` 复用 `search.Indexer`（SyncIssue/SyncSprint/SyncVersion/RemoveDocument），与 worker 增量同步共用同一投影逻辑。
- 退出码语义：只读发现漂移 exit 1（CI 告警）；`--fix` 修复成功 exit 0。
- **验证**（实测）：制造漂移（删 version 索引 + 插孤儿 999）→ 只读对账精确检出 → `--fix` 修复 → 复验一致 exit 0。✅
