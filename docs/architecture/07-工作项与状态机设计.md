## 1. 统一工作项模型（Issue Aggregate）

### 1.1 类型与差异字段矩阵

| 字段 | requirement | task | defect |
|------|:-----------:|:----:|:------:|
| name / description / state / priority / dates / labels / modules / assignees | ● | ● | ● |
| point / estimate_point | ● | ● | ○ |
| parent（WBS ≤3 层） | Epic→Feature→Story | 主任务→子任务→子子任务 | 主缺陷→子缺陷 |
| severity（1-5，必填） | — | — | ● |
| found_phase（必填） | — | — | ● |
| found_version / fix_version | — | — | ●（found 必填） |
| reproduce_steps（复现/期望/实际） | — | — | ● |
| root_cause_category（解决时必填） | — | — | ● |
| verifier | — | — | ○ |
| environment | — | — | ○ |
| category / delay_reason | — | ○ | — |
| actual_effort / remaining_effort | — | ○ | — |
| source（需求来源） | ○ | — | — |
| version（首次发布版本） | ○ | ○ | — |

DB 层用 `CHECK` 约束守底线（如 defect 必填 severity），完整校验在领域服务（可随项目配置扩展必填项）。

### 1.2 创建/更新用例流程

```
HTTP → TransitionGuard（前置中间件：租户+RBAC+项目归档检查）
  → IssueAppService.Create(ctx, cmd)
      1. 加载项目配置（状态集/必填项规则）   —— 缓存 proj:{id}:config
      2. 领域校验（类型字段矩阵、WBS 规则、必填项）
      3. 发号（project_sequences 原子自增）
      4. 写 issues + M2M（同事务）
      5. 写 issue_activities（created）
      6. 写 domain_events（issue.created，同事务 Outbox）
  → 响应 201
```

### 1.3 WBS 规则实现

- `parent_id` + 冗余 `depth`（1..3），插入时 `depth = parent.depth + 1`，>3 拒绝（`ISSUE.WBS_DEPTH_EXCEEDED`）。
- 循环校验：向上递归查父链（`WITH RECURSIVE` 深度≤3，成本可忽略）确认新父级不在自己的子树内。
- 级联删除：软删除父级时事务内级联子树；或"转移子项"模式（指定新父级，校验层级仍 ≤3）。
- **进度回写**：子项 state.group 变为 completed/cancelled 时触发 `ProgressRollupJob`（事件驱动，防抖 3s）：
  `parent.progress = Σ(完成子项 point) / Σ(全部子项 point)`，无 point 用计数；递归上卷。

### 1.4 关联与依赖

- `issue_relations`：duplicate / relates_to / blocked_by / start_before / finish_before / implemented_by（需求↔任务）。
- `issue_dependencies`：FS/SS/FF/SF + lag_days；写入时 DFS 检测环（任务规模内可行，>1k 节点退化为异步校验+标记）。
- 依赖约束提示（0→1 为"提示级"非"阻断级"）：前置未完成时流转 started 给出警告（前端确认可继续）；阻断级校验放自动化引擎规则由团队自选。

## 2. 状态机

### 2.1 内置模板（项目创建时复制）

**研发流（requirement/task）**：Backlog(backlog) → Todo(unstarted) → In Progress(started) → In Review(started) → Done(completed)；附加 Cancelled(cancelled)。
**需求评审流（requirement，可启用）**：草稿(is_draft) → 评审中 → 已采纳/已拒绝 →（采纳后进入研发流）→ 已验证。
**缺陷流（defect）**：新建(unstarted) → 确认(started) → 处理中(started) → 已修复(started) → 待验证(started) → 已关闭(completed)；任何状态 → 已拒绝(cancelled)；待验证/已关闭 → 重新打开(started)。

### 2.2 流转执行

```
Transition(from, to, ctx):
  1. 查 state_transitions 是否存在（项目×type 维度）→ 否则 ISSUE.INVALID_STATE_TRANSITION
  2. 角色校验（allowed_roles 非空时）
  3. required_fields 校验（缺陷→已修复：root_cause_category 必填；→待验证：fix_version 必填）
  4. 副作用：
     - to.group=completed → completed_at=now()；离开 completed → completed_at=NULL
     - 触发 ProgressRollup / Sprint 完成度缓存失效
  5. 写 activity（field=state, old→new）+ event（issue.status_changed）
```

### 2.3 自定义流转（Phase 2 末段）
项目管理员可在三套模板上增删 transition（不允许删模板内置的 group 锚点状态）；复杂条件（字段比较表达式）交给自动化引擎实现，状态机保持简单。

## 3. 活动日志与评论

- `issue_activities`：字段级 diff（verb=updated, field, old_value, new_value）；系统动作 verb=transitioned/attached/linked。
- 评论 `issue_comments`：富文本 JSON；@提及在保存时解析生成 `mention` 事件（通知域消费）。
- 时间线合并展示 activities + comments，按 created_at 倒序，游标分页。

## 4. 性能要点（对应单项目 100 万工作项目标）

| 场景 | 策略 |
|------|------|
| 看板查询 | `(project_id, state_id, sort_order)` 索引；仅取必要字段 + fields 裁剪；单页 ≤100 卡 |
| 拖拽排序 | `sort_order DOUBLE PRECISION` 中值插入；碎片化阈值（间隔<1e-6）触发异步重排 |
| 列表过滤 | 高频过滤字段全部独立列 + 复合索引；禁止 JSONB 字段进 WHERE |
| 详情页 | Redis 缓存 `issue:{id}:detail`（10min + 事件失效） |
| 进度回写 | 事件防抖批量，避免连环 UPDATE 热点行 |
| 活动日志 | 分区表 + 只查当前项目分区 |
