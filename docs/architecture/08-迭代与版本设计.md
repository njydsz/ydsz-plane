# 08 · 迭代与版本设计（S5–S6）

> 对应 Sprint 5/6；PRD §3.2/§5/§8.3/§8.4 的落地规格

---

## 1. 迭代（Sprint）生命周期

```
planned ──启动──▶ active ──结束──▶ completed
                    ▲                    │
                    └── 强制结束前可回退？不允许。active 唯一出口 completed
```

不变量：
1. 同一项目**同一时间只允许一个 active 迭代**（启动时校验 + Redis 锁 `lock:sprint:start:{project}` 防并发）。
2. active 迭代必须有 start/end_date；结束动作必须选择未完成任务处理策略（`backlog` | `next_sprint` | `keep`）。
3. 需求/任务/缺陷不得同时处于两个 active 迭代（默认开启，项目可配置关闭）。

### 1.1 关键用例

**启动** `POST /sprints/{id}:start`：校验当前无 active → 事务内置 active、记录启动快照（承诺故事点/需求/任务/缺陷清单）→ 事件 `sprint.started` → 通知参与者。
**结束** `POST /sprints/{id}:complete { "unfinished": "backlog" }`：事务内批量迁移未完成项 → 生成复盘数据（承诺/完成/加入/移除）→ `sprint.completed` → 速率统计更新 → 触发版本进度重算。
**中途加项**：`sprint_issues.added_midway=true`，复盘报告单列"中途加入对速率的影响"。

### 1.2 快照与燃尽图

- Cron 每日 00:05（Asynq Scheduler）对全部 active 迭代写 `sprint_snapshots`：
  ```json
  { "date": "2026-08-07", "total_points": 80, "done_points": 32,
    "by_state_group": {"backlog":0,"unstarted":30,"started":18,"completed":32},
    "added_points": 5, "removed_points": 0 }
  ```
- 燃尽图数据接口 `/sprints/{id}/burndown`：快照序列 + 理想线（起止线性插值）；当日无快照（启动日）用实时值补齐。
- 燃起图同表 by_state_group 渲染；CFD（Phase 3）复用该序列。

### 1.3 容量与速率

- `capacity`（人天）与饱和度 = Σ规划故事点 / capacity；拖拽规划时前端实时显示，超额红色高亮（非阻断）。
- 速率 = 已 completed 迭代的 done_points；推荐接口 `/sprints/suggest-capacity` 返回近 3/6 期均值与 P50，规划向导引用。

## 2. 版本（Version）

```
planning ──▶ active ──发布──▶ released ──▶ archived
```

### 2.1 版本属性
| 属性 | 类型 | 说明 |
|------|------|------|
| `name` | TEXT | 版本展示名（如"用户画像一期"） |
| `semver` | TEXT | 语义版本号（如 1.2.3），项目内唯一 |
| `description` | TEXT | 版本目标与范围描述 |
| `status` | TEXT | planning \| active \| released \| archived |
| `start_date` | DATE | 版本开始时间（可选） |
| `end_date` | DATE | 版本结束时间（可选） |
| `target_date` | DATE | 版本（版本的一个属性，可选） |
| `checklist` | JSONB | 发布检查清单 [{id,label,required,checked}] |
| `release_notes` | TEXT | Release Notes（发布时生成，可编辑） |
| `delivered_at` | TIMESTAMPTZ | 实际发布时间 |
| `archived_at` | TIMESTAMPTZ | 归档时间 |

### 2.2 聚合模型
- `sprints.version_id` FK: 一个版本聚合 1..N 迭代，一个迭代只属于一个版本（N:1 直关联，非 M2M）。
- 进度聚合（读时计算 + 事件失效缓存 `version:{id}:progress`）：
  `progress = Σ(版本内完成点数) / Σ(版本内总点数)`；范围 = Σ各归属迭代的需求/任务/缺陷。

### 2.3 发布动作 `:release`
1. 检查清单 `checklist` 全部勾选（缺项 422）。
2. 准出校验：致命/严重未关闭缺陷数 = 0（项目可配置阈值）。
3. 生成 Release Notes：按模板渲染 `已完成需求 / 修复缺陷 / 已知问题` 三段，落 `release_notes` 字段，可编辑。
4. 交付报告数据：`delivery_report` JSONB（缺陷数/通过率/准出率/迭代完成度明细）。
5. 状态→released（只读），事件 `version.released` → 通知 + Webhook + 自动化触发器。

### 2.4 缺陷版本联动
- 提缺陷时 `found_version` 默认当前 active 版本；`fix_version` 在流转"待验证"时必填。
- 版本详情"质量面板"：按 found_version 聚合缺陷数/严重程度分布（逃逸率计算的基础数据）。

## 3. 缓存与并发

| 场景 | 策略 |
|------|------|
| 迭代卡片进度 | 缓存 `sprint:{id}:progress`，issue 状态事件失效 |
| 版本进度 | 同上，键 `version:{id}:progress` |
| 启动/结束/发布 | Redis 分布式锁（SET NX PX 10s）+ DB 状态条件更新双保险 |
| 快照任务 | 单实例锁，防多 worker 重复写入（upsert by (sprint_id, snapshot_date)） |

## 4. API 摘要

```
POST   /sprints                      创建（planned）
POST   /sprints/{id}:start           启动
POST   /sprints/{id}:complete        结束（含未完成任务策略）
GET    /sprints/{id}/burndown        燃尽/燃起数据
GET    /sprints/suggest-capacity     速率建议
POST   /versions                     创建（semver 校验）
POST   /versions/{id}:release        发布（清单+准出+Notes+报告）
POST   /versions/{id}:archive        归档
GET    /versions/{id}/progress       聚合进度
GET    /versions/{id}/release-notes  查看/再生成
```
